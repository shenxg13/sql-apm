# 构建编排与发布设计

[Issue #29](https://github.com/shenxg13/sql-apm/issues/29) 的已确认 D1–D10 和实施授权覆盖本计划。
业务要求由[构建与版本](../../.project-wiki/features/baseline-versions.md)维护。

## 实施顺序与验证计划

1. 在固定 main 基线的隔离目录运行 1.5.0 真实数据导入和统计，保留临时实例，
   验证覆盖推导与旧覆盖表逐行相同，再执行 1.6.0 迁移并比较正式、观察统计。
2. 冻结 1.5.0 DDL，删除覆盖物理表，增加任务时间和阶段、构建层计数及覆盖推导；
   验证新库、各历史连续升级、重跑、catalog 漂移和结果保留。
3. 提取集群任务上下文，让导入、快照、统计、发布共用持锁连接；验证五种命令忙时拒绝、
   不同集群并行、各阶段进程被杀及持锁连接失效后的恢复。
4. 实现六项检查和原子发布，以及 full、rebuild、status、history 命令；
   对每项检查注入失败，验证零样本、仅调用、样本不足、失败停止和并发读取。
5. 按已确认首批多天及后续逐日场景在私有 PG17 执行两个集群共八次 full 和一次 rebuild，
   独立复算最终版本并测量阶段耗时、进程树峰值内存、版本存储与数据库增长。
6. 同步知识、操作手册和报告，执行普通、解析专项、数据库、Harness 和在线 PR 检查。

## 连接、事务与恢复

集群锁沿用 `hashtextextended(scope_id,1835101)` 的数据库会话锁，不设超时接管。
任务上下文持有唯一主写入连接，阶段接口接受该上下文；阶段切换不会重新获取锁。
失去持锁数据库连接后，该连接上的事务不能提交，也不自动重连或续算。
原文去重使用的独立连接仅保存可复用的不可变缓存，不写执行、任务或版本指针。
不同集群的任务锁互不阻塞；共享规则缓存按确定顺序短事务写入，不设跨集群长时规则锁。

新任务取得锁后，将残留 running 任务、导入尝试及未完成编排关联的构建记为 interrupted，
保留原因和原结果；失败重试创建新快照／构建。所有发布条件在持锁连接中验证，成功记录、任务终态和
当前版本指针同事务提交。仅以当前指针读取的查询看到切换前或切换后的完整版本。

## 覆盖、分区与成本

覆盖推导从 ConfigSnapshot 的窗口生成所需桶，从正式或观察统计取得已计算桶，差集为空桶。
不持久化每组五层 JSONB 覆盖；构建保存每层行数和分组数，检查时聚合核对，检测事后丢行。
发布检查扫描正式结果做逐组计数及数值自洽校验，不重算原始样本，不扫描观察结果。
这项扫描针对错误发布风险；复用一次分组聚合，避免按检查项反复读取全部统计。
仅信任构建回执无法发现保存后丢行；回读原始样本重算又超出六项自洽检查并重复主要计算成本，
因此核对已保存的正式结果。分组先聚合后作集合比较，同时识别缺组、多组及缺层，避免逐组重复探测。

新月份先独立建空表，再 ATTACH PARTITION，避免 CREATE TABLE PARTITION OF 的父表排他锁。
父表使用短时共享更新锁，普通 SELECT 不与之冲突；任务开始预建当月和次月分区。
DDL 与构建结果写入分开提交，不将分区锁持有到统计完成。

以上成本边界是 qualitative；真实端到端和分区并发检查完成后由验证报告提供 measured 证据。

## 检查与诊断细节

创建 Build 时六项 checks 初始化为 not_run／check_not_started；计算成功后逐项核对并整体保存。
检查通过不会修改样本门槛或观察统计。数值检查复用当前统计 CHECK 表达式对已保存行重验，
包含有限非负值、分位数／最小最大关系、所有指标的 NULL 原因、分母及覆盖数边界；
不以约束已存在代替实际校验，也不把指标重算和本次发布自洽检查混为一谈。
任务入场存在“已持锁但任务登记尚未提交”的短暂窗口；忙时仍记录拒绝，busy_task_id 可为空，
不等待登记或自动排队。已有任务可见时引用其标识。历史任务迁移不伪造未知完成时间。

发布事务同时写入任务终态，避免已提交版本却遗留 running 任务的窗口。若客户端丢失提交确认，
用 status 查询数据库的发布记录和当前指针判定结果，不自动重试或反向切换。
