# SQL 原文、明细与留存

## Summary

完整 SQL 原文精确去重与结构指纹是不同契约，留存边界独立于训练窗口。
设计 SQL 原文、执行／调用明细或历史版本存储时阅读。

## Source Of Truth

以下保留原知识索引各节的用户确认、日期、来源状态、证据限制和待定事项。
这些条款定义目标或事实，不表示相关产品功能已经实现；较早条款中的待定表述
应结合明确链接的后续确认阅读，不能覆盖后续已确认规则。
[知识变更记录](../log.md)用于追溯；涉及 Issue 时以其在线正文和评论核对任务契约。

## Contracts

### 已确认的 SQL 原文存储方式

- 确认日期：2026-09-25。
- 来源：用户对“SQL 原文在 PostgreSQL 中按完整内容精确去重保存，执行／调用
  明细引用原文记录；每次执行各自保留明细，同指纹下不同业务参数的原文分别
  保存，日志参数占位符原样保留；留存天数和清理另定”的建议回复“确认”。
- 来源状态：current；逻辑存储方式已确认，物理结构已交付，#18 已实现[精确原文与近似入库](../../docs/design/log-ingestion.md)。
- 对需要保留的执行／调用明细及可可靠取得的原文，在 PostgreSQL 中集中保存
  SQL 原文记录；内容完全相同的原文复用同一份文本，对应明细引用该原文记录。
- 每次真实执行或调用按既有单位独立保留时间、耗时、状态等明细，不因 SQL
  原文相同而合并次数。调用仍不作为额外的完整 SQL 执行，未知耗时沿用 NULL。
- 精确去重依据完整原文内容相同，不先去空白、去注释或替换业务常量再合并
  原文。相同结构指纹下，日期、订单号等业务常量不同的原文各自保存，不限于
  每个指纹只留一份或少量代表文本；这些文本仍可归入同一结构基线。
- 日志中已有的 `$1`、`$2` 等绑定参数占位符原样保留，不从 DETAIL 还原实参，
  不把参数化文本称作已恢复业务实际值的 SQL。
- 存储时的原文去重与结构指纹归组是不同用途；原文记录的标识不作为结构
  指纹失败时的替代。共享文本也不合并不同集群、数据库、用户或计时类别的统计。
- 基线版本继续仅保留统计和构建信息，不按每次构建复制执行明细或 SQL 原文。
- 本条限定可靠原文的逻辑保存方式，不改写原始日志、不补造缺失或不完整 SQL，
  不改变执行／调用识别、历史展示及训练资格。无法可靠归属的日志问题仍按
  既有诊断规则处理，不因能存文本就进入基线。
- 2026-09-27 确认的[近似观察](sql-fingerprints.md#已确认的观察用近似指纹)保留已记录
  原文／字节与来源证据；不完整片段不冒充完整 SqlText，不再补取完整 SQL。
  用户于 2026-09-29 确认先交付近似存储，再由 #18 同次导入可靠与近似结果，观察统计另行处理。
  [结构 1.2.0](../../docs/design/postgresql-storage.md#近似观察结构-120)已实现原字节、规则、结果及
  证据／事件引用表；不改变本节完整原文精确去重语义。原字节按完整内容复用，结果再区分
  规则和结构失败原因；每次执行／调用仍各自保留，不依赖重新读取 CSV 回填。
- 首期自动清理暂缓，原始 CSV 由人工管理，见下节；保留天数及后续清理与
  引用处理与压缩方式继续待定，产品精确去重写入已由 #18 实现；已交付结构见物理设计。问题记录的存储
  留存也继续另行确定；30 天训练窗口不自动作为留存期限。
- 参考[两集群日志分析](../../docs/reports/cluster-log-analysis-2026-09-24.md)：119 的
  耗时记录 SQL 累计文本为 1,065.14 MiB，精确去重后 289.80 MiB；120 为
  1,191.02 MiB 和 576.21 MiB。测量覆盖全部耗时记录文本，含阶段重复及黑名单
  文本，不是合格明细存储量或 PostgreSQL 实测容量，不含行、索引、WAL、备份等。

关联条款：[已确认的首期留存与自动清理边界](sql-storage.md#已确认的首期留存与自动清理边界)；[已确认的 SQL 检索与分组选择](../features/sql-search-and-views.md#已确认的-sql-检索与分组选择)。

### 已确认的首期留存与自动清理边界

- 确认日期：2026-09-25。
- 来源：用户对“首期暂缓自动清理，执行／调用明细、去重原文和历史基线暂不
  自动删除，原始 CSV 人工管理；实际入库测量后再确定期限和清理方案”的建议
  回复“确认”。
- 来源状态：current；首期留存边界已确认；导入与容量测量已由 #18 实施，清理仍未实施。
- 首期暂缓自动清理；程序暂不自动删除执行／调用明细、去重 SQL 原文和历史
  基线版本。原始 CSV 由人工管理，首期不建立程序自动删除原始日志的任务。
- 默认 30 天仍仅作为可调整的训练窗口，不作为自动删除界限。窗口之外已保留
  的数据可继续用于历史回看，不因本轮训练不使用就自动删除。
- 完成首轮真实入库后，结合各类数据的实际占用、增长情况及历史回看需求，
  分别确定原始日志、明细、SQL 原文和基线版本的保留期限及清理方案。具体
  天数和后续清理实现未在本次固定，不把暂缓清理解释为永久留存承诺。
- 已有日志／文本字节和压缩测量不等于数据库实测容量；首轮实际入库及相应
  容量观察见 #18 验证，不能据此宣称已验证长期容量。
- 既有原文精确去重、按集群管理版本、正常训练筛选和历史查看规则继续适用。
  问题记录的具体存储留存、后续清理时的引用处理与压缩归档仍待落实。

### 已接受的增长与统计分区（2026-09-30）

来源：[Issue #21 R1 用户确认](https://github.com/shenxg13/sql-apm/issues/21#issuecomment-5903278085)，
由 [Issue #25](https://github.com/shenxg13/sql-apm/issues/25) 明确要求同步。
用户接受生产环境两集群导入明细约 1.3 GiB／天（约 470 GiB／年），以及每次模板或规则变更约
0.7 GB 的增长；留存和清理设计暂不急。这是依据既有入库与缓存观察接受的运行量级，
年增长为外推，不是完整一年实测，也不表示永久留存承诺。

用户同时确认统计结果全部完整保存；mpp_statistic、mpp_build_coverage 按“集群＋构建月份”
分区，一年约 24 个分区／表（两集群），不按每次构建、时间层次或计时类别拆表。
瘦身移除 statistic_id 文本代理主键及重复 scope_id／normalization_id／profile；
保留构建优先和分组历史查询索引。1.4.0 的自然键与关联校验见[物理设计](../../docs/design/postgresql-storage.md)。
导入侧大表仍不分区，首期自动清理继续暂缓。

2026-09-30 [后续范围确认](https://github.com/shenxg13/sql-apm/issues/25#issuecomment-5914482826)进一步移除
逐统计行重复保存的 `sufficiency` JSONB，按原构建封存配置和公式版本派生完整门槛结果，
见[统计契约](baseline-statistics.md#统计完整保存与首期边界2026-09-30)。统计结构仍为未发布的 1.4.0。

### 统计存储量级接受（2026-10-01）

用户[确认接受统计结果的存储量级](https://github.com/shenxg13/sql-apm/issues/25#issuecomment-5917051665)：
总存储在 4–5 TB 以内没有压力，后续通过调整历史版本保留周期控制总量。
这是新增的统计容量接受决定；上节导入明细／规则缓存的增长观察继续保留。

确认依据中，[新结构全量验收](../../docs/reports/baseline-statistics-2026-10-01.md)的 measured 值为：
120 集群七天数据单次构建约 7.8 GiB（统计约 4.3、覆盖约 3.2、构建分组约 0.3 GiB），
119 单次约 1.0 GiB。120 三十天窗口单次约 29 GiB 是 modeled 外推，依据样本缓存观察到的
每天约 12 万新增分组、约 21.6 万活跃分组；约 85% 分组只执行一次。
容量接受不把这些外推改为完整三十天或全年实测，也不承诺永久保存每个历史版本。

保留周期与清理设计仍为后续工作。`mpp_build_group` 不分区，不能随月分区一起删除；
届时须单独协调构建分组关联的清理及引用处理。
