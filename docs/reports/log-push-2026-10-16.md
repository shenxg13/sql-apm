## 实施与验证计划

按已确认契约依次实现：master 只读推送及清单、收取核对及恢复和清理、定时衔接、手册与知识同步。
验证对应 U2–U11 的失败与中断用例，再执行真实私有 SSH／PG 的 U12–U14，回归 U15。
性能证据等级为 qualitative：仅元数据核对和同文件系统改名；有界端到端耗时只记录，不设生产吞吐门槛。
实施选定 `pushDays` 上限 366、登录账号固定 `sfmon`、制表符清单及 `push.complete.tmp`／`push.complete`；
其余范围沿用在线契约。操作步骤见[每日运行](../runbooks/daily-run.md#mpp-端推送)。

## 原模板逐段对照（U1）

原文为 Issue 正文末尾的截图转录，不是从生产导出的完整模板；不在仓库复制原始截图或生产参数。
新模板见 [`daily/push-logs.sh`](../../daily/push-logs.sh)。

| 原模板段落 | 实施后的对应行为 | 变动依据 |
| --- | --- | --- |
| `#!/bin/bash`，begin 输出；读取 `RCLONE_DEST_PATH`、`RCLONE_BUCKET_NAME`、`PLAN_ID`，打印路径、计划、源目录和应用用户 | 保留 Bash、变量名字和 `echo` 风格；增加明确失败输出函数 | 范围 1、8 |

| `backupArray=($backupFilePath)`，逐路径查存在 | 仍按空白拆目录；先只读遍历完整文件集合、按文件名日期过滤，记录大小和同名冲突，再连接 | 范围 3、6、7；重复名必须在推送前发现 |
| 以 `su - $appUser -c` 执行远端 SSH | 保留应用用户及 SSH；远端登录账号替换为固定 `sfmon`；变量作 shell 引用 | 范围 4、7 |
| 远端 `mkdir -p 推送目录; rm -fr 推送目录/*` | 同样建目录及删除 `目录/*`；使用 `&&` 确保 mkdir 失败不被后续 rm 的成功掩盖，错误码原样退出 | 范围 1 的逐步失败退出、5；删除范围未缩小 |
| 每目录 `ls -l` 和 `scp -r -p` 整目录 | 元数据列表由只读文件筛选取代；逐个 `scp -p` 普通日志、平铺落地；保持路径开始／结束、scp 成败 echo | 范围 3、6、8 |
| 任一步失败 `exit $exitCode` | SSH、SCP、标志写入错误码原样退出；管道启用 pipefail 避免清单发送失败被隐藏 | 范围 1、6 |
| 拷完直接退出，没有完成信号 | 清单始终放 shell 内存，最后从 stdin 发给远端 cat，临时名改正式名；空集合也发布；打印每日期和总数量 | 范围 6–8 |

脚本文本的写入／删除命令只在发给远端 SSH 的命令字符串中：`mkdir`、`rm`、`cat >`、`mv`；
master 本地只读目录、元数据、文件、hostname 和日期，变量／数组只驻内存。没有本地临时文件。
没有增设 SSH 选项或改变应用用户的 SSH 配置。

## 自动验证

命令从仓库根运行。日志保留于忽略目录 `var/issue65/`；私有 SSH/PG 与临时 systemd 单元在退出时清理。
新增测试均使用合成输入；没有读取生产日志。

| 验收 | 验证与观察 |
| --- | --- |
| U2–U5 | `scripts/daily/verify_push.py` 使用真实回环 sshd、`sfmon` 登录；su、hostname 和今天由测试替身提供。推送前后逐路径比名字、大小、mtime、权限和 SHA-256。默认 7／3／24 天、轮转、排除、缺天、同名冲突、空路径、不合法天数、SCP 失败及标志写入失败均覆盖。错误码 23 原样返回；正式标志命令为临时名改名。 |
| U6–U11 | `tests/test_log_intake.py` 核对缺标志、格式、缺文件、大小、额外日志、未知主机；检查 inode、已有标记不动、无覆盖、冲突日不动。真实子进程在第一次 rename 后暂停并 SIGKILL，再运行补完。超时以测试传入当前时刻推进 25 小时验证，未实际等待 24 小时；旧源 mtime 不提前删除。检查其他文件、子目录、FIFO、链接、根目录外文件保留、路径重叠与立即拒绝并发。 |
| U10、U12 | 两 master 共用落地根，相同多级 dest_path 结构。逐日模拟一次真实 SCP 失败、一次未收取、一次收取后才推送，再运行真实 `daily run`。29 个唯一日批、29 个文件、145 条记录与人工输入按日批状态、文件摘要／字节数、记录数对照一致；`daily status` 无推送引起的问题。 |
| U13 | 24 天首推产生全部对应文件和标记；日常空 `pushDays` 重推 7 天后，接收目录每个文件和标记的 inode 不变。 |
| U14 | 生成器四种配置组合和缺配置拒绝均覆盖。真实用户定时器到时启动，收取因不完整推送退出 1，仍先拉取、再运行；新收取日期成功入库，服务结果 success。测试单元随后移除。 |
| U15 | 每日运行单元检查、私有 PG 的 26 项日常及 16 项恢复检查、真实 SSH 的 16 项原拉取检查。`sql_apm/`、数据库、看板与原拉取脚本没有差异。完整 Harness 与项目检查见本 PR 验证记录。 |
| U16–U17 | 开发机建立落地根、配置、首次推送及收取，按手册格式执行；生产平台界面与公钥安装由用户核对／操作。手册覆盖首次 23–24 天、留存与推送天数、日常恢复、权限及观察路径；开发说明与日志获取主题同步。 |

复现命令：

```bash
.venv/bin/python -m unittest discover -s tests -p test_log_intake.py -v
.venv/bin/python scripts/daily/verify_push.py --sshd-root var/issue54/sshd --timer
.venv/bin/python scripts/db/verify_daily.py
.venv/bin/python scripts/db/verify_daily_recovery.py
.venv/bin/python scripts/daily/verify_fetch.py --sshd-root var/issue54/sshd
PATH="$PWD/.venv/bin:$PATH" scripts/quality/project_checks.sh
PATH="$PWD/var/harness-tools/bin:$PATH" scripts/quality/check.sh
```

`--sshd-root` 指向已解包的 openssh-server；不需要安装到系统，准备方法见[开发说明](../design/daily-run.md#验证入口)。
项目解释器下的 125 项单元测试全部执行；CI 的精简 Python 环境没有产品数据库驱动，生成器检查与既有同类测试一样明确跳过，
其四种组合及真实定时衔接在开发机项目解释器下验证，不把 CI 跳过当作执行通过。
端到端运行时间见 `var/issue65/push-verification.log` 的 `seconds`，它包含等待定时器的时间，不能作为传输性能基准。
