## 为什么相同阶段有两种日志形式

上游 `check_log_duration`（2893 行开始）结合 `log_duration`、耗时门槛和
`was_logged` 选择不输出、只输出耗时，或者输出带阶段／SQL 的详细形式。

在用户提供的 `log_duration=on`、`log_min_duration_statement=1min`、
`log_statement=all` 设置下：

- Parse、Bind 的分支以 `was_logged=false` 调用检查函数，通常在一分钟内
  输出简略 duration，达到门槛则输出显式 parse／bind。
- Simple Query、Execute 已在前面按 `log_statement=all` 记录了请求，因而
  即使运行很久，完成处也可以只输出简略 duration；不能用是否写出 execute
  字样或是否超过一分钟判断它属于哪个阶段。

当前日志符合该模式：`:2219`／`:2603` 的最大值均小于 60 秒；119 的 109 条、
120 的 18 条显式 Parse 全部来自 `:2224` 且超过 60 秒，120 的 54 条显式 Bind
全部来自 `:2608` 且超过 60 秒。这是配置、源码分支和实际记录的一致性证据，
不是直接读取业务连接生效参数的结果。

## 1946 与 2843 的关键区别

### 1946：简单查询请求整体

上游 `exec_simple_query`（1601 行开始）遍历请求中的语句，循环退出并完成
相应收尾后才进入 1922 行的 duration 分支。因此这一位置对应的多语句耗时
覆盖整个请求，不能按每个分号拆出同样耗时的样本。空请求也可能走到日志分支，
所以识别该位置不免除文本与训练资格检查。

Q、P、B、E 消息分别设置各自的计时起点；简单查询请求中的解析、计划和执行
包含在 Q 请求区间中，而 Execute 的计时不自动包含先前独立 P／B 消息。

### 2843：Execute 调用返回，可能只完成一段

上游 `exec_execute_message` 在 2778 行调用 `PortalRun`。若完成，则发送
CommandComplete；若因取数条数限制而未完成，则发送 PortalSuspended。两条
分支之后**都会**执行 2819 行开始的 duration 逻辑。

[PG 9.4 扩展协议说明](https://www.postgresql.org/docs/9.4/protocol-flow.html#PROTOCOL-FLOW-EXT-QUERY)
同样说明 Execute 可指定最大返回行数，portal 暂停后可再次 Execute 续取。
因此这里的“完成”只能先解释为本次协议调用返回。

定向复查全部 46 个文件发现实际续取，不只是理论可能：

| 观察项 | 119 | 120 |
| --- | ---: | ---: |
| `execute fetch from` 消息 | 13,737 | 277 |
| 上述消息来源 | `postgres.c:2764` | `postgres.c:2764` |
| 最近同会话同 SQL 的对应 `:2843` duration | 13,737 | 277 |

这些数是续取调用／日志计数，不是受影响 SQL 执行实例数。**仅过滤带 fetch
标记的调用仍不够**：同一分段执行的第一次 Execute 也可能只是第一段。不能
把它当成整条 SQL 耗时，或把后续各段分别算成完整 SQL 的重复执行。
本轮未实现 portal 生命周期还原，也没有决定分段耗时求和、客户端等待计入
与否、何时认定完整取数等产品口径。

## 首次 Execute 与续取能否精确关联

用户进一步询问 2843 首次与续取的关联精度。结论需要区分三层：把一个
Execute 消息与其 duration 配对、把首次及续取串成同一 portal 的调用链、
证明这条链覆盖完整成功执行。已有证据支持部分实例的前两层，但没有验证
覆盖全部日志的通用关联规则，也没有因配对成功而证明第三层。

同提交上游源码的 `2764` 对应消息格式包含首次／fetch 标记、prepared
statement 名称，以及非空时的 `/portal` 后缀；前一个名称本身不是 portal
实例标识。`2843` 的简略 message 字段只有 duration；整条 CSV 仍有独立 SQL 字段，
单次调用分类需结合会话内有序日志关联。
不能只用 SQL 指纹、SQL 原文或进程号认定同一次执行，应考虑日志来源、完整
会话身份、portal 生命周期、首次／续取标记与文本等证据。

复读此前两个有界案例，119 的记录 88,962、88,988、88,991，以及 120 的
152,073、152,158，均有具名 portal 后缀，同案例内 statement／portal 标签、
会话及精确 SQL 一致；对应 2843 的 message 字段均仅含 duration，独立 SQL
字段仍有文本。120 首次 execute
与其 duration、后续 fetch 的命令编号已经不同，故不能把命令号相等作为
普遍必需条件；这也不证明忽略命令号后即可全量无歧义关联。

[PG 9.4 扩展协议](https://www.postgresql.org/docs/9.4/protocol-flow.html#PROTOCOL-FLOW-EXT-QUERY)
规定 portal 可以关闭、重建，未命名 portal 也可被后续 Bind 替换。名称不能
脱离会话和生命周期当作永久执行 ID。日志缺口、文件边界截断调用链或无法
判断生命周期时，应保留关联不确定性，不能按相同指纹强行合并。

上游 CommandComplete 与 PortalSuspended 两条分支都会走到同一个简略
耗时输出；Close 协议处理成功时发送 CloseComplete，也没有在所检查的
分支中增加常规 LOG 级别的完整性标记。因此，最后一条 2843 或不再出现续取
不能单独证明结果已完整取完；客户端也可能停止续取并关闭 portal。即使能
关联已观察到的调用，累加所得也只是这些调用的耗时之和，不自动成为完整
执行耗时，且不包含调用之间的客户端等待区间。

此前全量扫描的 13,737／277 条续取配对数，只验证最近同会话同 SQL 的
execute-fetch 消息与其 duration 的关系，不是全量首次到全部续取生命周期
关联已完成的计数。现有首期训练资格与阶段处理决策不因此改变。

本轮有界只读复查输出位于
`/tmp/sql-apm-execute-correlation-boundary-20260924.json`，只保存位置、时间、
布尔相等关系、标签是否带 portal 后缀与耗时，不保存 SQL、身份或名称原文。
两文件复查前后大小及 mtime 不变；未实现关联器或请求用户提供私有源码。

## 2843 的独立 SQL 字段与单次配对覆盖

用户因“2843 只有 duration”的简略表述追问是否没有完整 SQL。应明确区分
CSV 的 message 字段与独立 SQL 字段：本批 30 列记录中，第 19 列是 message，
第 25 列保存 SQL。前者仅含 duration，不表示后者为空；2764 的主要补充是
首次／续取标记和相关名称，不是通常需要从它才能得到 SQL。

初轮全量统计中，119 的 671,465 条、120 的 457,073 条 2843 记录，独立 SQL
字段均非空。非空并不保证完整或正确：120 有 121 条词法闭合问题候选；不能
将它们都断定为截断，也不能把其余记录的词法通过当作与客户端原文一致的
证明。绑定参数仍按既定规则保留占位符，不借此宣称已还原实际参数。

本轮有界复读 119 记录 88,962／88,986 与 120 记录 152,073／152,153。
两条 duration 消息分别仅含 3,865.664 ms 和 30,848.270 ms，但各自独立
SQL 字段分别有 12,918 与 837 字节，且与对应 2764 的 SQL 字段完全相同。
会话相同，120 案例的命令号不同；复查前后输入文件大小及 mtime 不变。
临时脱敏结果：`/tmp/sql-apm-duration-sql-field-replay-20260924.json`。

从既有全量诊断结果汇总单次配对，而非本轮再次全量扫描：

| 集群 | 2843 总数 | 找到候选配对 | 未得到候选配对 |
| --- | ---: | ---: | ---: |
| 119 | 671,465 | 671,465 | 0 |
| 120 | 457,073 | 457,064 | 9 |

候选方法为同会话最近相关开始消息、相容的消息类型及精确 SQL 相等，不强制
命令号相等。120 的 9 条中，6 条没有最近相关开始消息，3 条类型或 SQL 不符。
这些是当前诊断的未匹配分类，未逐条证明根因，不据此认定日志丢失或永远无法
关联。表中衡量的是候选配对覆盖，不是由独立执行真值验证的匹配准确率。

单次 2764→2843 配对与跨多次调用的 portal 生命周期还原不同。在同一来源、
可靠会话身份和日志顺序下，可以以单次调用的开始／返回边界建立配对，并用
原文和上下文核对；不能用相同结构指纹、最近时间或命令号相等单独替代验证。
错误、缺口或无法消除的歧义应保留未确认状态。配对成功仍不证明整个 portal
已完成。此说明澄清先前表述，没有实现配对器或改变首期训练资格。

## 与日志时间差的交叉检查

按会话内最近的相应开始消息及精确 SQL 比较，不强制命令号相等。这里的匹配
只是取证支持，不是已经验证的通用执行 ID。令差值为：

`duration 日志时间 − 开始消息日志时间 − duration 数值`。

| 来源／消息类型 | 119 可比较记录 | 119 差值中位数 ms | 120 可比较记录 | 120 差值中位数 ms |
| --- | ---: | ---: | ---: | ---: |
| `1946` 与 statement | 819,577 | -4.520 | 1,551,778 | -4.327 |
| `2843` 与首次 execute | 657,728 | 0.017 | 456,787 | 0.006 |
| `2843` 与 execute fetch from | 13,737 | -0.077 | 277 | -0.097 |

这进一步支持 2843 对应当前 Execute 调用。日志时间差不等于计时器读取值，
存在少量较大偏差和未匹配记录，不能用中位数去修正每个样本，也不能宣布开始
时间已精确还原。1946 的计时起点可以早于 statement 消息，源码也在开始计时
后进行解析等工作，再输出 statement。

## 与 activity 比较有关的补充

上游对每个协议消息重设 statement 起点，Execute 再调用 `pgstat_report_activity`。
[同提交 pgstat.c](https://github.com/greenplum-db/gpdb-archive/blob/9a08259bd1836f0cf5ba935e7e0030a5a9c0a54b/src/backend/postmaster/pgstat.c#L2715)
在有 SQL 文本时，用当前 statement 起点更新活动开始时间字段。因此，发现
Parse／Bind 很长，并不能单独推出 activity 中的 Execute 必然包含这些前置
阶段，也不意味着应把这些耗时简单相加来对齐 query_start。

这补充了此前关于可能存在时间偏差的讨论。HashData 现网 activity 尚未同期
对照，推算开始时间继续标记为 derived；本轮不改已确认的 Parse／Bind 简化
假设或时间归属。需要保持关注的是：Simple Query 与 Execute 的计时范围不同，
且 Execute 可能分段。

## 实施含义与未完成项

- 可以将四个位置按上述含义列入当前版本样本的高置信分类依据，保留版本、
  源码位置及证据来源。它们不应在所有构建中无条件硬编码。
- 1946 是 Simple Query 正常完成路径；仍按既定规则检查单条／整批、空请求、
  SQL 质量及其他训练资格。2219、2603 继续不作为正常执行样本。
- 2843 是 Execute 调用计时。已知分段／续取场景必须与整条 SQL 的完整耗时
  区分；首次调用也不能因没有 fetch 标签就自动通过完整性检查。
- 分类规则与“是否额外建立阶段基线”是两个问题。用户此前提出阶段分组，
  尚未确认新增第五个基线维度，本轮调查不自动变更。
- 剩余工作集中于分段 Execute 的业务口径与可靠识别、其他内部来源、未知
  构建的处理。取得 HashData 私有源码不是继续当前四项分类讨论的必要前提。
