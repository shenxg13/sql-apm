## 数据库实测

命令：`.venv/bin/python scripts/db/verify.py`。

结果：**58 项原有存储检查、39 项迁移检查及独立异常实例清理检查通过**。
初版约束、精度、原文复用、统计五层和 17 指标、未知／零、SCRAM 重跑及发布引用
在新表名下重新验证。迁移检查覆盖：

| 检查 | 实际结果 |
| --- | --- |
| 默认及不同名称 | sql_apm 默认库／schema／账号，以及 apm_upgrade_db／apm_upgrade_store／apm_upgrade_role 均完成含数据升级。 |
| 新库与旧库一致 | 新建 1.1.0 与升级后结构均通过同一个完整目标 catalog 校验。 |
| 表、索引及约束命名 | 总计 41 张表：14 张 mpp_ 专属表、27 张其他表；旧专属表名不存在，专属索引和约束名称均有前缀。 |
| 行数据与对象身份 | 对全部 40 张业务表（含空表）逐表比较 JSON 行内容；关系 OID／relfilenode 和约束 OID 保留。未扫描生产数据。 |
| 公共表引用 | config_snapshot 和 problem 含数据引用仍关联正确的 MPP 表，并拒绝悬空引用。 |
| 版本及历史发布 | 保留 1.0.0 的 SHA-256 和首次应用时间，新增 1.1.0 记录；当前版本仍指向 V1／PUB1。 |
| 重复执行 | 重复 upgrade 及 schema 后数据、对象身份和两条版本时间保持不变。 |
| 拒绝错误状态 | 普通初始化拒绝隐式升级；旧列漂移、错误摘要、额外未知版本和同名目标表阻止迁移；已升级库的摘要漂移仍被拒绝。 |
| 真实锁冲突 | 另一个连接持有旧表读锁，升级因 5 秒锁等待超时失败；旧数据及对象状态保留。 |
| 中途失败 | 在第一张表改名后注入 SQL 失败，整笔回滚；全部旧表、行、对象身份及版本记录保留。 |
| 提交前失败 | 在目标校验和版本插入后注入失败，结构及版本一起回滚；恢复脚本后可成功重试。 |
| 临时对象及实例 | 成功及失败均不残留预期／旧结构校验 schema；正常及独立异常路径均停止并清理实例。 |

测试入口为 `scripts/db/verify.py`；迁移检查由 `tests/database/migration.py` 承担。
本次最终运行的临时目录均已停止并删除，日志只在本地临时目录保存。

## 证据边界

迁移以一笔事务完成元数据改名；初始化／检查仍通过小型空 schema 的 catalog 对比
判断兼容性。资源影响以定性说明及上述小规模实测为准，没有生产规模基准。
需要维护窗口暂停访问并串行执行，不承诺在线无阻塞、不提供成功提交后的自动降级。
新旧应用 SQL 名称需要随版本切换；未增加旧名视图，也未增加其他系统业务表。

业务导入、解析、指纹、统计计算及发布编排仍未实现。本次没有验证真实日志容量、
分区迁移、生产留存策略、断电／SIGKILL 或停止工具自身故障下的清理能力。
各系统独立表仍共享数据库实例资源，不等于计算、存储或故障的完全隔离。
