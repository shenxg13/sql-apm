# SQL 原文、明细与留存

## Summary

完整 SQL 原文精确去重与结构指纹是不同契约，留存边界独立于训练窗口。
设计 SQL 原文、执行／调用明细或历史版本存储时阅读。

## Source Of Truth

以下保留原知识索引各节的用户确认、日期、来源状态、证据限制和待定事项。
这些条款定义目标或事实，不表示相关产品功能已经实现；较早条款中的待定表述
应结合明确链接的后续确认阅读，不能覆盖后续已确认规则。

## Contracts

### 已确认的 SQL 原文存储方式

- 确认日期：2026-09-25。
- 来源：用户对“SQL 原文在 PostgreSQL 中按完整内容精确去重保存，执行／调用
  明细引用原文记录；每次执行各自保留明细，同指纹下不同业务参数的原文分别
  保存，日志参数占位符原样保留；留存天数和清理另定”的建议回复“确认”。
- 来源状态：current；逻辑存储方式已确认，表结构、导入和去重存储尚未实现。
- 对需要保留的执行／调用明细及可可靠取得的原文，在 PostgreSQL 中集中保存
  SQL 原文记录；内容完全相同的原文复用同一份文本，对应明细引用该原文记录。
- 每次真实执行或调用按既有单位独立保留时间、耗时、状态等明细，不因 SQL
  原文相同而合并次数。调用仍不作为额外的完整 SQL 执行，未知耗时沿用 NULL。
- 精确去重依据完整原文内容相同，不先去空白、去注释或替换业务常量再合并
  原文。相同结构指纹下，日期、订单号等业务常量不同的原文各自保存，不限于
  每个指纹只留一份或少量代表文本；这些文本仍可归入同一结构基线。
- 日志中已有的 `$1`、`$2` 等绑定参数占位符原样保留，不从 DETAIL 还原实参，
  不把参数化文本称作已恢复业务实际值的 SQL。
- 存储时的原文去重与结构指纹归组是不同用途；原文记录的标识不作为结构
  指纹失败时的替代。共享文本也不合并不同集群、数据库、用户或计时类别的统计。
- 基线版本继续仅保留统计和构建信息，不按每次构建复制执行明细或 SQL 原文。
- 本条限定可靠原文的逻辑保存方式，不改写原始日志、不补造缺失或不完整 SQL，
  不改变执行／调用识别、历史展示及训练资格。无法可靠归属的日志问题仍按
  既有诊断规则处理，不因能存文本就进入基线。
- 首期自动清理暂缓，原始 CSV 由人工管理，见下节；保留天数及后续清理与
  引用处理、压缩方式、具体去重实现和物理表结构继续待定。问题记录的存储
  留存也继续另行确定；30 天训练窗口不自动作为留存期限。
- 参考[两集群日志分析](../../docs/reports/cluster-log-analysis-2026-09-24.md)：119 的
  耗时记录 SQL 累计文本为 1,065.14 MiB，精确去重后 289.80 MiB；120 为
  1,191.02 MiB 和 576.21 MiB。测量覆盖全部耗时记录文本，含阶段重复及黑名单
  文本，不是合格明细存储量或 PostgreSQL 实测容量，不含行、索引、WAL、备份等。

关联条款：[已确认的首期留存与自动清理边界](sql-storage.md#已确认的首期留存与自动清理边界)；[已确认的 SQL 检索与分组选择](../features/sql-search-and-views.md#已确认的-sql-检索与分组选择)。

### 已确认的首期留存与自动清理边界

- 确认日期：2026-09-25。
- 来源：用户对“首期暂缓自动清理，执行／调用明细、去重原文和历史基线暂不
  自动删除，原始 CSV 人工管理；实际入库测量后再确定期限和清理方案”的建议
  回复“确认”。
- 来源状态：current；首期留存边界已确认，数据库导入、容量测量和清理尚未实施。
- 首期暂缓自动清理；程序暂不自动删除执行／调用明细、去重 SQL 原文和历史
  基线版本。原始 CSV 由人工管理，首期不建立程序自动删除原始日志的任务。
- 默认 30 天仍仅作为可调整的训练窗口，不作为自动删除界限。窗口之外已保留
  的数据可继续用于历史回看，不因本轮训练不使用就自动删除。
- 完成首轮真实入库后，结合各类数据的实际占用、增长情况及历史回看需求，
  分别确定原始日志、明细、SQL 原文和基线版本的保留期限及清理方案。具体
  天数和后续清理实现未在本次固定，不把暂缓清理解释为永久留存承诺。
- 已有日志／文本字节和压缩测量不等于数据库实测容量；首轮实际入库及相应
  容量观察仍属后续工作，不能据此宣称已验证长期容量。
- 既有原文精确去重、按集群管理版本、正常训练筛选和历史查看规则继续适用。
  问题记录的具体存储留存、后续清理时的引用处理与压缩归档仍待落实。
