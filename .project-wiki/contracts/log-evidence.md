### 已确认的日志记录口径

- 确认日期：2026-09-22。
- 来源：在询问现网日志是否记录所有已完成 SQL 的耗时、还是仅记录超过时长门槛的
  SQL 时，用户回答“记录所有”。
- 来源状态：current；这是用户提供的现网事实。已检查下述生产样本，用户已于
  2026-09-23 补充下列日志配置；尚未直接读取业务连接的生效配置或取得完整执行
  对照，未独立核验“所有已完成 SQL 均被记录”的覆盖保证。
- 现网日志记录所有已完成 SQL 的执行耗时，不仅记录超过慢 SQL 时长门槛的执行。
- 用户提供的配置为 `log_duration = on`、`log_min_duration_statement = 1min`、
  `log_statement = all`、`log_min_error_statement = error`。这些值来自本次用户
  说明，不是通过日志时长分布推测，也不是本地或远程查询结果。
- 按 [PG 9.4 日志说明](https://www.postgresql.org/docs/9.4/runtime-config-logging.html)，
  `log_duration = on` 会记录已完成语句的耗时，`1min` 不构成所有 duration
  记录的最低时长门槛；`log_statement = all` 另行记录语句，文本不一定在耗时
  消息中重复。扩展协议各阶段可分别计时，因此该配置仍不能证明一条 duration
  就是一条业务 SQL 或整个多语句批次的完整耗时，CSV 字段的计时归属仍需验证。
- 用户补充：生产 HashData 中单次 SQL 执行可能持续数小时，完成记录可能落入
  后续日志文件或导入批次。首期按下述已确认的时间估算假设取得开始时间，
  不以跨文件寻找开始记录为前提；其他执行关联及必要上下文的处理另行落实。
- 日志记录范围与训练样本范围分别确定：SQL 黑名单继续生效，基本训练资格见下述
  已确认规则；日志字段到执行状态、耗时及执行实例的具体映射另行确认。

关联条款：[已确认的五类计时统计与 Parse／Bind 纳入](timing-and-grouping.md#已确认的五类计时统计与-parsebind-纳入)；[已确认的 Execute 单次配对与调用分类统计](timing-and-grouping.md#已确认的-execute-单次配对与调用分类统计)。

  6 个文件中失败；保留原始字节后可解析全部 CSV 边界。234 条记录含不可解码
  字节，其中 95 条耗时记录的 SQL 字段受影响；不能静默忽略字节或视为已修复。
- 匹配 `duration: ... ms` 的记录共 1,103,323 条，不代表同等数量的实际执行。
  其中 7,892 条 SQL 字段为空；1,725 条 SQL 恰为 1,023 字节，存在引号、括号、
  注释或末端 UTF-8 序列不完整的实例。不能直接沿用测试样本中 SQL 均非空且
  未发现明显截断的观察，也不能把这些记录都认定为业务完成记录。
- 找到显式 Parse 耗时 3 条、Bind 耗时 22 条，最长分别为 166,208.955 ms 和
  587,916.647 ms。另有 15,000 条耗时来自 autostats 源码位置。未标阶段的
  记录仍需识别；源码行号本身不构成已验证的阶段映射。
- 生产样本包含数小时耗时。最大记录约 26 小时 39 分钟，但 SQL 为 1,023
  字节且括号不闭合，不能直接纳入训练；另有约 8 小时 43 分钟的 SELECT

  有同时包含 INSERT 等业务语句的实例。按文本首关键词排除整段，或把一条
  duration 分配给每个子语句，都不能替代执行归属判定。用户随后确认下述
  单条／批次指纹及混合批次黑名单规则，实际日志到计时单位的映射仍需验证。
- 候选会话／命令组合存在不同 SQL，同一组合和 SQL 也可能出现多条 duration。

- 全部原文件逐文件 gzip 后约 219.50 MiB；耗时记录 SQL 原文字节累计约

- 既定训练资格、推算开始时间归属及参数占位符边界继续适用。生产观察要求

  无法提供 HashData 私有源码。本轮已从官方 Greenplum 归档读取固定提交
  `9a08259bd1836f0cf5ba935e7e0030a5a9c0a54b`，公开备份测试将其标记为
  `6.20.3+dev.4.g9a08259bd1`；结合全部 46 文件的定向复查，形成
  [专项核查报告](../../docs/reports/hashdata-duration-source-mapping-2026-09-24.md)。
- 当前样本的高置信语义映射为：`1946 → exec_simple_query`，
  `2843 → exec_execute_message`，`2219 → exec_parse_message`，
  `2603 → exec_bind_message`。四类及显式 Parse／Bind、前置 statement／execute
  共八处日志位置均与上游消息格式行形成一致偏移。函数名来自源码对照，日志中
  对应函数字段为空；这不是取得 HashData 对应源码后的逐行核验，不能外推到
  所有构建或自动成为已实现的解析契约。此结论补充上节初轮候选分类。
- 1946 的 Simple Query duration 位于多语句循环之后，对应请求整体；多语句
  仍按已确认的整批规则，不向子语句分摊耗时，文本质量及其他训练资格继续适用。
- **2843 是一次 Execute 调用的耗时，不保证整条 SQL 完整执行。** 上游在
  CommandComplete 或 PortalSuspended 两分支后均记录 duration；实测 119 有
  13,737 条、120 有 277 条 `execute fetch from` 续取消息，均有最近同会话同 SQL
  的 2843 耗时。它们是日志／调用数，不是独立 SQL 执行数。
- 有界复查确认同会话、同 SQL、同 portal 的首次 Execute 及多次续取都产生
  2843 耗时。不能只删后续 fetch 记录而自动把首次调用当作完整 SQL；分段样本的
  完整性、关联及耗时口径仍待落实，不在本轮自动求和或增加新训练单位。
- `log_statement=all` 下，Simple Query／Execute 的请求已先记录，慢执行也
  可以只输出简略 duration；Parse／Bind 在达到门槛时才出现详细阶段标签。
  因而显式 parse／bind 的条数不是各阶段调用总次数。
- 上游每个协议消息重设 statement 起点，Execute 再更新 activity 的开始字段。
  不能仅凭 Parse／Bind 很长就断言必须累加阶段才能与 query_start 对齐。
  HashData 同期 activity 尚未核验；保留 derived 标记及既定时间归属和首期
  忽略 Parse／Bind 的假设，Simple Query 与 Execute 计时范围差异仍须注意。
- 当前基本 SQL 分组仍是集群、数据库、用户和结构指纹四维；后续用户确认的
  Execute 首次／续取及 Parse／Bind 分类现已纳入下述五项统计分组。识别重点
  还包括 Execute 分段完整性、其他内部来源及版本变化，
  不再把取得 HashData 私有源码作为这四类语义分类的必要前提。

- 进一步核对首次／续取关联：2764 消息中的 prepared statement 名称与可选
  portal 后缀需区分，2843 的 message 字段只有 duration，但独立 SQL 字段
  仍有文本。两个已复查案例均有
  相同具名 portal／会话／精确 SQL，但 120 案例从首次消息至 duration 的
  命令号发生变化。关联应结合会话内顺序和 portal 生命周期，不能以相同指纹
  或命令号替代执行身份；已有续取配对总数不代表全量 portal 链已还原。
  同一 2843 路径不区分 CommandComplete 与 PortalSuspended，仅最后一条
  duration 或没有后续 fetch 不证明完整成功结束；已关联调用之和也不自动
  作为完整执行样本。见专项报告的关联边界补充，未改变已确认训练资格。

- 澄清 2843 的字段与单次配对：这批 CSV 的独立 SQL 字段在 119 全部
  671,465 条和 120 全部 457,073 条 2843 记录中均非空，不能把 message
  只有 duration 误解为整条记录没有 SQL；120 仍有 121 条词法闭合问题候选，

### psql 多语句计时的现场测试（2026-09-23）

- 来源：用户本轮提供的两张终端照片，一张显示 psql 调用及正常返回结果，另一张
  显示 Master 日志输出；来源状态为 current，仅限照片中的可见案例。尚未取得
  该次测试的原始 CSV 文件，以下是目视核对，不是完整日志扫描或解析器验收。
- 客户端使用单个 `psql -c` 字符串一次提交以下两条无业务数据访问的测试 SQL：

  ```sql
  SELECT pg_sleep(2);
  SELECT pg_backend_pid() AS pid, pg_sleep(5);
  ```

- 日志照片显示 `2026-09-23 16:29:31` 左右记录包含两条 SQL 的 statement，
  `16:29:38` 左右记录 `duration: 7031.575 ms`，该耗时记录也携带两条 SQL 的
  完整文本。7,031.575 ms 即 7.031575 秒，与两次等待合计约 7 秒一致。
- 这支持将本次 psql 整体提交路径中的该条 duration 解释为整批请求的完成耗时，
  不能把它分别赋给两个子语句，也不能从一个总耗时推导任意业务子语句的独立耗时。
  如果后续采用批次样本，其结束时间减 duration 推算的是批次开始时间。
- 照片中的日志命令使用 `grep pg_sleep` 过滤；不含该文本的记录可能被遗漏，
  因此不能据此证明一次执行只产生一条 duration。此例也不覆盖其他客户端、
  扩展协议、混合 DML/DDL 批次或失败中断情形，不自动形成通用完成记录识别规则。
- 此案例提供计时证据；用户随后明确确认下述整体批次指纹和混合批次黑名单
  规则，该确认不扩大照片的验证范围。保留成功完成、耗时完整、执行关联可靠
  的既有训练资格。
- 照片作为会话中的来源保留；项目知识仅记录测试 SQL、时间和耗时，不转录
  主机名、账号、数据库名或进程标识。
