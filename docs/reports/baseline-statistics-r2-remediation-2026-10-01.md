## 实现与契约

- R2-F001：新增[只读批量 SQL](../../sql_apm/storage/statistics_sufficiency.sql)，每个 Build 读取一次封存配置，
  通过现有完整函数验证五层门槛并解析类型化数值，随后逐行比较样本数和活跃日／周数，
  返回自然键及 basic_met、p95_met、p99_met。完整函数仍用于单组详情和原因。
- 门槛采用 numeric，不把合法的大整数配置强制转成 bigint。版本和门槛校验复用原函数，
  未增加持久表、缓存或数据库函数；结构仍为 1.4.0，默认门槛和统计公式不变。
- R2-F002：按[用户确认](https://github.com/shenxg13/sql-apm/issues/25#issuecomment-5917051665)，
  [存储主题](../../.project-wiki/contracts/sql-storage.md#统计存储量级接受2026-10-01)记录总存储 4–5 TB
  以内无压力的接受。保留周期与清理继续待后续设计，明确 mpp_build_group 不分区，不能随月分区删除。
- R1-F001、R1-F002 已由 R2 独立核验为 fixed，本次不改变其实现与处置。
  历史报告和知识日志原条目保留；本轮追加当前知识与新测量。

[设计](../design/baseline-statistics.md#门槛结果的数据库派生)与

## 有界实测方法（measured）

命令为 `.venv/bin/python scripts/db/benchmark_statistics_sufficiency.py --output NEW_FILE`，
默认使用固定种子 20260930、60,000 个合成组，经产品 calculate_group 和 ResultWriter 生成
834,999 行真实形状的统计。约 20% 组仅排除，另含少量 20,000 次执行的大组；
时间落在七天内，以三十天窗口计算全部五层。该分布用于查询比较，不代表生产分布。

脚本创建私有 PostgreSQL 17.10，使用单张临时叶表形状的关系，复制统计列、CHECK 和两类索引。
配置和 Build 使用临时关系；不连接既有实例。结束时已停止并清理私有数据库。
Python 为 3.9.5；work_mem=4MB、jit=on，max_parallel_workers_per_gather=2。
临时表查询本身不使用并行扫描。配置、参数、逐层分布、每次耗时、源码摘要和
EXPLAIN (ANALYZE, BUFFERS) 计划保存在[机器记录](data/baseline-statistics-r2-query-cost-2026-10-01.json)。

先按自然键逐行比较两个路径的三个标记，共 834,999 行、2,504,997 个布尔值，差异为 **0**。
两个聚合查询各预热一次，之后交替顺序测五次，包含本地驱动 execute／fetch 的耗时；
完整路径使用与原全量验收一致的 lateral jsonb_to_record 调用，避免把一次完整函数重复执行三次。
单组查询抽取 2,000 组，预热一轮后测五轮，每轮记录每组平均耗时。

| 查询路径 | measured 口径 | 耗时 |
| --- | --- | ---: |
| 单组完整 ThresholdResult | 五轮每组均值的中位数 | 0.349 ms／组 |
| 全构建完整函数聚合 | 五次中位数；范围 9,071.961–9,238.063 ms | 9,116.744 ms |
| 全构建批量 met 聚合 | 五次中位数；范围 236.607–245.053 ms | 240.039 ms |

聚合加速约 **37.98 倍**；完整函数约 10.918 µs／行，批量约 0.287 µs／行。
单独采集的带执行分析计划耗时 323.793 ms，不混入普通计时中位数。
计划显示 selected_build 生成一行一次、ConfigSnapshot 扫描一次，validated 与 limits 各五行一次。
批量比较不逐行解析 JSON 或调用完整函数。

测量限定为本机热缓存合成数据；不包括数据准备、导入、统计构建、持久写入 WAL、
真实分区遍历和并发负载。临时关系、生产数据分布、缓存状态、规划和 I/O 的差别可能改变结果。
本次没有测旧物理 JSON 路径，也不把独立 R2 的 833,625 行探针与本次不同分母拼成同一次测量。
调试时首轮在 VACUUM 的事务上下文失败；修正连接生命周期后完整重跑，仅最终成功记录计入本表。

## 规模外推（modeled）

仅以同一热缓存每行成本线性外推，假定数据形状和计划不变：

| 假设统计行数 | 完整函数聚合 | 批量 met 聚合 |
| --- | ---: | ---: |
| 120 已有构建的 5,850,925 行 | 63.9 秒 | 1.68 秒 |
| 再按七天至三十天同比例放大到约 25,075,393 行 | 273.8 秒 | 7.21 秒 |

第二行只是按 30／7 放大行数的场景，不是生产三十天行数预测；新分组比例和桶覆盖会改变行数。
这些值均非生产实测或延迟承诺。查询耗时外推与用户已接受的存储预算是不同证据，不能互相替代。

## 正确性与回归

[回归辅助模块](../../tests/database/statistics_batch.py)由既有统计验证入口运行：

- 用真实写入的默认和自定义快照构建验证两路径逐行一致，旧 Build 继续使用原门槛；不存在的 Build 返回空集。
- 用回滚隔离的临时关系，逐层验证计数和覆盖的下界、等值、上界，以及零样本／零门槛；
  日期数与周数刻意不同。批量、完整函数和独立 Python oracle 三方一致。
- 门槛及覆盖最低值大于 bigint 的合法配置仍得到相同结果；Build ID／partition_id 联合选择防止串入其他分区。
- 未知／缺失公式版本、缺失门槛及负门槛均拒绝。原完整 ThresholdResult 的字段与原因回归保持通过。
