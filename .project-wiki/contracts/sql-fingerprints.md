# SQL 结构指纹与归一化

## Summary

已确认的常量、参数、对象名、配置值与注释规则统一用于导入和 SQL 检索。
实现指纹、函数字典或 SQL 输入检索匹配时阅读。

适用范围：以下为首期 HashData 契约；设计后续来源接入时，参照
[多类型系统接入约束](../decisions/project-scope.md#已确认的多类型系统接入扩展约束)。

## Source Of Truth

以下保留原知识索引各节的用户确认、日期、来源状态、证据限制和待定事项。
这些条款定义目标或事实，不表示相关产品功能已经实现；较早条款中的待定表述
应结合明确链接的后续确认阅读，不能覆盖后续已确认规则。
[知识变更记录](../log.md)用于追溯；涉及 Issue 时以其在线正文和评论核对任务契约。

## Contracts

### 已确认的首版指纹模块交付边界

- 确认日期：2026-09-26；来源状态：current。
- 来源：用户在讨论指纹与离线基线程序的实施拆分后，对交付形式、语法覆盖、
  Hint 比较方式和验收力度四项建议回复“确认”；由
  [Issue #9](https://github.com/shenxg13/sql-apm/issues/9)承接实施计划和验收。
  这是已确认交付要求；当前实现与限制见下文“可靠归一化实施记录”。
- 同一项目内单独交付 SQL 解析、归一化和结构指纹能力，提供可供后续程序调用的
  Python 模块，以及接收 SQL 文本／文件的简单诊断命令；输出归一化表示、指纹、
  规则版本和诊断结果。归一化表示是派生结果，不能替代源 SQL。
- 数据库读写、生产日志导入及计时配对、基线计算与发布留给后续任务；导入、
  基线构建和 SQL 检索复用这一模块。输入输出及版本依据遵循
  [离线数据契约](offline-data-contract.md#c06归一化与分组)，本模块无须连接数据库。
- 以 MPP（HashData）及现有 119／120 日志为依据，覆盖常见查询、写入、DDL 和
  多语句批次，交付具体语法支持清单及正反用例；不能只实现 SELECT 示例，也不
  承诺所有数据库方言。关键语法若无法可靠支持，须明确提出范围调整，不能仅将
  必需形式列为不支持就声称完成验收。已有词法类别调查不是完整语法支持证据。
- Hint 按后文普通格式与注释处理中的保守比较规则处理，不因此扩大为执行计划或
  语义等价分析。常量、函数、对象、类型转换、批次及失败处理继续遵守既有契约。
- 验收包含合成用例的应合并／应区分、重复运行稳定性和失败边界，以及现有日志的
  有界代表性重放。记录来源、抽样边界、分母和可靠／不支持／失败情况，对代表性
  结果进行人工核对；生产原文留在本地忽略区域，不能用抽样结果声称全量覆盖。
  本任务不要求全量日志性能验收，不设置未经调查的覆盖率门槛。
- 2026-09-27，用户在讨论全量解析覆盖调查后要求“开始全量遍历解析”，追加确认
  对现有119／120的46个日志执行完整EOF读取和解析覆盖核查。按完整SQL原文字节
  精确去重并保留批次、出现次数与来源；分别报告结构返回、不支持、异常与资源限制。
  这项诊断扩展已同步在线Issue正文，未增加全量性能门槛或改变归一化规则；临时本地
  索引只服务诊断，不代表产品日志导入或持久化缓存已实现。
- 解析器、哈希算法、占位编码、具体接口及文件划分由实施阶段按上述要求选择和
  验证，不要求用户逐项决定。依赖遵守 Python 3.9.5 约束；语法支持、Hint 识别或
  实现限制若会改变已确认范围，仍须先按在线契约的范围变更流程处理。

### 已确认的观察用近似指纹

- 确认日期：2026-09-27；来源状态：current。
- 来源：用户引用“无法取得完整文本时，允许生成单独标记的近似指纹……用于聚合观察，
  ……与可靠结构指纹分开，暂不用于正常基线的自动异常判断”的建议，明确回复
  “我觉得可以按这个处理，不必再尝试取得完整sql了”。本条为已确认需求，近似能力已按下述实施记录交付；观察统计尚未实现。
- 对无法可靠解析／归一化、但仍有可可靠处理的已记录文本，允许生成独立的近似表示和
  近似指纹。只处理边界能确定的内容；不确定的词法片段或上下文保守保留，同时保存
  原始文本／字节、原结构失败原因及不完整／不确定标记。不保证所有拒绝输入均可生成结果。
- 不再尝试从其他日志、客户端或数据库补取完整 SQL，不拼接片段，不补括号或引号，
  不恢复绑定实参。既有日志导入、字段选择和 Execute 计时配对仍按各自契约实施，
  不因本条增加补取 SQL 的任务，也不取消计时归属所需的关联。
- 近似与可靠结构结果须有明确区分的类型、规则版本及比较上下文。近似成功不把原有
  结构失败改为 reliable，不伪造完整 SqlText，不冒充可执行 SQL；缺失输入、无可可靠
  处理内容或近似处理失败时仍保留诊断。非法规则配置及资源失败不能包装成正常成功。
- 近似分组用于观察次数和可靠取得的耗时分布，不进入正常基线训练或自动异常判断，
  不因样本量达标升级为可靠。不同集群、数据库、执行用户及计时类别分别观察；保留
  失败／未知状态，不由解析拒绝推断执行失败。相同片段可能属于不同完整 SQL，近似
  相同只表示观察分组，不保证完整 SQL 等价。
- 日志文本出现次数不等于执行次数。有可靠事件身份及计时依据时才能统计对应请求／
  调用次数和耗时，不能重复计算同一事件，不能把整批耗时分配给可解析子句；依据不足
  时只保存能够确认的记录级事实与原因，不补造耗时或成功状态。
- 本条调整此前“失败不提供文本指纹”的绝对表述，保留“不用原文哈希或近似指纹替代
  可靠结构指纹建立正常基线”的边界；此前讨论的独立原文正常基线方案未获本次确认。
- [Issue #9](https://github.com/shenxg13/sql-apm/issues/9)交付近似能力、调用与诊断接口
  及边界验证；具体词法规则、可处理范围、输出编码与字段由实施文档和正反用例固定。
  日志导入、观察统计计算／展示及必要的持久化扩展由后续程序落实，不据本次确认宣称
  已有数据库结构支持近似结果，也不把近似值填入现有可靠 Fingerprint／Group。

2026-09-27 用户随后要求“开始实施，在实施完成后重新验证一遍之前失败的sql”。
已实现 `sql-approximate/1` 的保守词法表示、简单 WHERE／UPDATE 直接业务值替换、原字节
保留和独立结果接口；[接口说明](../../docs/design/sql-approximate.md)列出未替换位置及限制。
[重放报告](../../docs/reports/mpp-approximate-2026-09-27.md)记录8,909个拒绝中的8,736个
近似可用、173个不可用，原失败原因全部保留；384个已修复输入的完整结构摘要不变。
这不是可靠结构归一化通过率，不表示观察统计、存储或整个 Issue #9 已完成。

### 首期 schema / search_path 处理边界

- 确认日期：2026-09-22。
- 来源：用户对“保持现有四维分组、保留显式 schema 和表名、不推断隐含 schema、
  暂不还原复杂会话状态，并接受可能混入同一基线的限制”的建议回复“确认”。
- 来源状态：current；这是已确认的首期处理边界，指纹已按下述实现交付，会话重建不在范围内。
- SQL 中显式写出的 schema 和表名保留在结构指纹中，用于区分不同的显式对象引用。
- 对未写 schema 的对象引用，不猜测或补全其归属；首期不通过完整重建
  `search_path` 等会话状态来还原实际访问对象。
- 已知限制：在计算集群、数据库、执行用户及 SQL 结构指纹相同时，因隐含 schema
  差异而实际访问不同表的执行可能被归入同一基线。
- 现场是否存在这类用法尚未核实；首期按上述边界处理，不以完成该调查作为前置条件。

技术背景参考：[Greenplum CSV 日志字段](https://knowledge.broadcom.com/external/article/296967/how-to-load-greenplum-pg_log-into-a-tabl.html)
及 [PostgreSQL 9.4 search_path 规则](https://www.postgresql.org/docs/9.4/runtime-config-client.html)。
这些文档支持日志与对象解析的能力边界，不代表已经验证现网的全部会话行为。

关联条款：[已确认的基线分组维度](timing-and-grouping.md#已确认的基线分组维度)。

### 已确认的首期绑定参数处理边界

- 确认日期：2026-09-23。
- 来源：用户对“首期保留 SQL 中的 `$1`、`$2` 等占位符，暂不还原实际绑定参数，
  用完成记录中的 SQL 文本生成结构指纹、用 `duration` 建立耗时基线，不以
  `execute` 参数明细的精确关联作为前置条件”的建议回复“确认”。
- 来源状态：current；这是已确认的首期范围，归一化已实现，导入及绑定值恢复未实现。
- 首期使用选定完成记录中的 SQL 文本作为结构指纹输入；源 SQL 保留原有参数
  占位符，派生的归一化表示遵循下述已确认规则。使用该记录的 `duration` 作为
  首期执行耗时，并按已确认方法推算开始时间。
- 首期不从 `execute` 的 `DETAIL` 恢复或代入实际绑定参数，不要求为此将耗时
  记录与参数明细一一配对；参数值未随完成记录提供，不单独构成训练排除原因。
- 参数化 SQL 的文本可能保留占位符，不能将其展示或描述为已经还原实际参数的
  执行语句。WHERE 条件及 INSERT／UPDATE 中已确认范围的业务常量按下述原则
  归一化；原有占位符与业务常量在这些位置的指纹归并已于 2026-09-24 确认，
  具体算法及其他未确认的规范化细节继续落实。
- 完成记录识别、其他必要的执行关联及此前确认的训练资格继续适用；本次不改变
  原始日志或 SQL 文本的留存安排。

关联条款：[已确认的原生参数与业务常量归并](sql-fingerprints.md#已确认的原生参数与业务常量归并)；[已确认的指纹生成失败处理](../features/log-ingestion.md#已确认的指纹生成失败处理)。

### 已确认的业务常量归一化

- 确认日期：2026-09-23（WHERE 业务常量）；2026-09-24（INSERT／UPDATE 业务值）。
- 来源：用户对同一 SQL 或批次中 WHERE 日期、订单号等业务常量的处理，明确
  选择“业务常量归一化，按结构合并”；后续对将 INSERT 写入值、UPDATE 赋值
  中直接作为列值的业务字面常量也纳入归一化，保留结构信息及特殊值的建议回复
  “确认”。
- 来源状态：current；已确认归并原则及其统计边界，当前算法见下述实现记录。
- 同一 SQL 或批次结构相同、仅下列已确认位置的显式业务常量不同，首期将这些
  值归一化为占位标记，归入同一个结构指纹；其他基线分组维度仍须相同：
  WHERE 条件中的业务常量，以及 INSERT … VALUES 和 UPDATE … SET 中直接
  作为列值或赋值的业务字面常量，例如数字、字符串。
- 对象名、列名、表达式结构、显式类型转换以及批次语句顺序保留；IN 列表长度的后续例外见下节。此确认不等于
  将 SELECT 投影、函数参数等其他语法位置的常量也无条件归一化。
- 例如，两次独立执行 `UPDATE orders SET status = 'paid' WHERE id = 1001;`
  与 `UPDATE orders SET status = 'closed' WHERE id = 1002;` 可生成相同结构
  指纹；实际聚合仍要求集群、数据库、执行用户及计时类别相同。
- 首期接受不同业务参数导致的耗时差异进入同一组统计，不按这些业务常量的
  具体取值再拆分基线。相同指纹不代表所有参数下执行耗时或执行计划相同。
- 此规则只改变指纹归并，不合并真实执行次数，不改变已确认的单条／整批粒度，
  不从日志参数明细还原实参，也不改写原始输入或确定其留存方式。SQL 检索沿用
  已确认的与日志入库相同的归一化规则。
- UPDATE 赋值中的业务数据适用上述归一化；混合批次的 SET 配置值及显式
  LIMIT／OFFSET 数量继续按下述规则保留。其余非函数参数常量按下节已确认的
  保留规则处理，函数参数仍由字典 Issue 单独确定；不能把 SQL 中所有数字或
  字符串都无条件替换。占位标记编码及其他具体规范化细节待落实；原有 `$n`
  参数与业务常量的指纹归并按后文已确认规则执行。

关联条款：[已确认的归一化规则版本与更新处理](../features/baseline-versions.md#已确认的归一化规则版本与更新处理)。

### 已确认的 WHERE IN 列表粗分桶与 Hint 编码清理

- 确认日期：2026-09-28；来源状态：current。
- 来源：[Issue #11](https://github.com/shenxg13/sql-apm/issues/11) 正文及
  [确认记录](https://github.com/shenxg13/sql-apm/issues/11#issuecomment-5864401115)；用户确认全部范围及 B1–B8。
  R1 整改时用户追加确认保留 Hint anchor 的同桶例外，见[范围修订记录](https://github.com/shenxg13/sql-apm/issues/11#issuecomment-5865613229)。
- 在已确认的 WHERE 业务常量位置，IN／NOT IN 列表全部元素均归一化为业务值时，
  按长度 1、2–10、11–100、>100 四桶归并；桶标记进入结构指纹，字面常量与原生 `$n` 可混用。
  这是前述“表达式结构保留”对 IN 列表长度的明确例外；没有采用任意长度折叠或 log2 分桶。
- 列表含列、表达式、函数、NULL、子查询或其他非裸业务值元素时，整个列表保留既有结构。
  显式转换仍保留转换节点和类型，不因内层值已替换就去除转换或折叠此类列表。
- SELECT／UPDATE／DELETE 的 WHERE 及 CTE／子查询各自的 WHERE 适用；函数参数、
  SELECT 投影、JOIN／HAVING、聚合 FILTER、控制子树和 IN 子查询的外层结构保持原规则。
  已知聚合 FILTER 仍按 v3 替换业务值，但保留 IN 列表元素及长度；其中可遍历子查询的独立 WHERE
  适用分桶。`INSERT … ON CONFLICT … DO UPDATE … WHERE` 按更新条件分桶；冲突目标
  `ON CONFLICT (…) WHERE` 的推断谓词继续整体保护，不混用两种 WHERE。
  多行 VALUES、ANY／ARRAY、其他常量位置及观察用近似路径均不改变。
- 可靠 Hint 的全局 gap 移出哈希，位置身份只由已有 anchor 决定；内容、所属语句、局部间隙、
  词法结构摘要、带符号业务值归并及明确拒绝边界保持不变，不改为 AST 节点锚定或推断 Hint 等价。
  **同桶归并的已确认例外：** IN 分桶不重写 anchor；Hint 在同语句列表之前或之后时，
  列表长度仍可改变 anchor，产生不同指纹。批次边界 Hint 同样保留完整位置身份。
  该例外由用户在 R1 整改中明确接受，不以真实样本暂未受影响替代规则确认。
- 用户接受同桶不同列表长度可能对应不同执行计划、增加组内耗时离散的权衡；此次不评估执行计划
  或耗时相近性。只改变结构分组，实际执行记录不合并，其他统计维度继续分别计算。
- 版本升级为 `sql-normalization/4`；正式解析能力名由实施确定为 `mpp-adapter/9`。

诊断，只有解析明确拒绝才尝试独立近似结果，不将内部异常或非法配置包装成近似成功。

固定上下文含算法／解析能力／依赖版本、字典规范摘要和不可变规则引用；调用方须保存
`rule_snapshot()` 内容，不能只留摘要。根目录 `requirements.txt` 锁定 pglast 7.18，
SQLGlot 继续仅作候选实验依赖。核心不访问数据库、不补取 SQL、不生成可执行 SQL，
观察统计、导入和基线编排仍未实现。

[接口及支持矩阵](../../docs/design/sql-normalization.md)定义输出字段、构造异常、512 KiB
输入边界和特殊函数。该次实现仅以全局 token 间隙编码 Hint，后续 R1 发现除拆组外还会
错误合并不同位置；现行修复及限制见下一节，旧验证不覆盖这个缺陷。
[验证报告](../../docs/reports/sql-normalization-2026-09-27.md)记录1,832条有界输入中1,810条
可靠、22条拒绝、1,566个可靠组及完整结构守恒检查。此为本地实现和固定样本证据，不表示
生产部署、全量归组准确率、全部 MPP 方言支持或 Issue 已完成合并。

### R1 整改实施记录（2026-09-28）

用户要求“进行R1整改”后，针对独立评审的 `I9-R1-F001`、`I9-R1-F002` 完成实现修复，
验收范围保持不变；评审结论与问题处置保留在[PR #10](https://github.com/shenxg13/sql-apm/pull/10)。
该次版本为 `sql-normalization/2`、`mpp-adapter-probe/6` 和 `sql-approximate/2`，字典仍为1.0.1。
可靠 Hint 以所属语句、局部间隙和保留括号的完整 token 种类序列摘要绑定位置；批次边界独立
标记。完整 AST 继续参与身份，不以词法摘要或原文哈希替代；详细编码和保守拆组限制见
[可靠接口](../../docs/design/sql-normalization.md)。近似路径判断语法上下文时跳过 Hint，
输出保留原 Hint 及顺序，整个函数／显式转换保护不被 Hint 打断；见
[近似接口](../../docs/design/sql-approximate.md)。新旧版本身份不能直接混比。

[整改报告](../../docs/reports/sql-normalization-r1-remediation-2026-09-28.md)记录原8组反例、
同类扩展及新的1,832条有界回放。可靠／拒绝状态和1,566个可靠组的成员集合与旧样本相同，
不是旧指纹值相同，也不是全量语义准确率证明。历史全量解析和近似报告保留，未重复115万条
全量扫描或把旧版本证据覆盖为新版；实现方验证不替代后续独立 R2。

### R2 整改实施记录（2026-09-28）

独立 R2 已确认两个 R1 问题修复，但发现 `I9-R2-F001`：版本2锚点把一元负号单独计数，
导致含 Hint 的正负业务值拆组，违反 A3；原文档“正负数字可能保守拆组”不能缩减验收。
用户要求“进行R2整改”后，当时实现升级为 `sql-normalization/3`、`mpp-adapter-probe/7`，
`sql-approximate/2` 和字典1.0.1不变。依据 PG 数值常量节点及源位置确认折叠的负号，
同时规范锚点摘要、全局间隙和局部间隙；保留真正的运算符和括号，不推断业务值所在位置。
Hint 位于被折叠负号之后时明确拒绝可靠结果，避免不同位置合并；完整边界见
[接口说明](../../docs/design/sql-normalization.md)。

[新验证报告](../../docs/reports/sql-normalization-r2-remediation-2026-09-28.md)记录72组原反例
归并恢复、198及728组位置回归、UTF-8与MPP源位置回映、1,832条固定回放以及5,333条含
Hint 标记输入的分组对照。真实样本未出现原缺陷，因此正负业务值正确性由定向合成用例证明；
不能用真实组数未变替代缺陷验证。另补充可靠／近似路径对 `/* + … */`、`-- + …` 的既有
识别差异及测试，不改变近似规则。验收范围和历史证据保留，实施验证不代替独立 R3。

### 收敛裁决整改实施记录（2026-09-28）

R3 发现 PG 合成常量缺少源位置时，负号映射误拒绝有效 SQL，导致 `I9-R2-F001` 残留及
`I9-R3-F001`。Maintainer 的[裁决 adj-9-10-20260928](https://github.com/shenxg13/sql-apm/issues/9#issuecomment-5862909714)
冻结 B1–B5 批量范围；用户要求“进行adj整改”后，本次只调整该源位置判定及对应规则上下文、
测试和证据。A1–A10 不变，普通轮次已消耗3，后续为独立的一次性终验，不新增 R4。

当前解析版本为 `mpp-adapter-probe/8`，可靠算法保留 `sql-normalization/3`、近似算法保留
`sql-approximate/2`、字典保留1.0.1。只把具有非负整数源位置的数值常量用于映射折叠负号；
无源位置的 PG 合成常量跳过映射，完整 AST 仍保留。常量位置／跨度／适配替换冲突的三项
诊断用于防御内部映射不一致，不能作为拒绝有效合成常量 SQL 的理由；Hint 位于折叠负号
内部的明确拒绝仍保留。准确边界及规则依据见[接口说明](../../docs/design/sql-normalization.md)。

[整改报告](../../docs/reports/sql-normalization-adj-remediation-2026-09-28.md)保留57例残留、
1,173例广覆盖变体、180例嵌套表达式与兼容替换、三项防御不变量、完整旧账本回归及
1,832／5,333条真实输入差分。历史报告保持原样；实施方验证不代替独立终验，
最终结论和执行状态以在线裁决、评审与 `status:*` 标签为准。
