# 每日运行操作说明

对应 [Issue #54](https://github.com/shenxg13/sql-apm/issues/54)，结构版本 1.12.0。本文说明怎样让基线服务器每天自动完成一轮工作，
以及怎样查看结果和处理问题。它供试用，也是 `v0.3.0` 随包手册“每日自动运行”一章的底稿；离线安装和目标机上的步骤由
[Issue #52](https://github.com/shenxg13/sql-apm/issues/52) 给出。文中的集群、来源和路径都是例子。

## 它做什么

每日运行是一条命令，运行一次就退出，没有常驻进程。它按配置里的顺序逐个处理集群，一个集群做完再做下一个：

1. **导入。** 把接收目录里有齐全标记、还没有导入成功的日期，从早到晚逐天导入，每天一个批次。
2. **构建发布。** 已导入成功的最新日期比当前版本的截止日晚了至少“构建间隔”那么多天，就构建并发布一次，截止日取最新日期。
   积压多天也只出一个版本。
3. **清理版本结果。** 过期月份的统计结果按训练配置里的保留月数清理，规则与 `cleanup --execute` 相同。
4. **删除原始文件。** 已整批导入成功、早于保留天数的日期，删除它在接收目录里的文件和标记。
5. **留下记录。** 每次运行看到了什么、做了什么都写进数据库，用命令行或 Grafana 的“运行状态”看板查看。

它不做的事：不判断文件是否齐全（由齐全标记表示），不拉取日志（由传输脚本或人工完成），不发通知。
人工的 `import`、`full`、`rebuild`、`cleanup` 照常可用，可以与每日运行并存。

## 一、配置

每日运行有自己的一份 JSON，引用现有的导入配置和训练配置：

```json
{
  "version": 1,
  "import_config": "import.json",
  "training_config": "training.json",
  "sources": {
    "mpp-119": {"directory": "/data/sql-apm/inbox/119"},
    "mpp-120": {"directory": "/data/sql-apm/inbox/120"}
  }
}
```

- `sources` 列出参与每日运行的日志来源和各自的**接收目录**。来源必须已经登记在导入配置的 `sources` 里
  （所属集群、构建串、时区和人工声明仍在那里登记一次）；导入配置的 `batches` 可以是空的 `{}`，每日运行自己登记批次。
- 训练配置的 `clusters` 要包含这些来源所属的集群。窗口天数、样本门槛、黑名单、排除时段和保留月数都取训练配置。
- 增加一个同版本的 MPP 集群：在导入配置里登记它的集群和来源，在训练配置的 `clusters` 里加上它，再在这里加一行接收目录。

其余各项都有默认值，需要时再写：

| 配置项 | 默认 | 写法 |
| --- | --- | --- |
| 构建间隔 | 1 天 | `"build": {"interval_days": 7}`；按集群：`"build": {"clusters": {"120": 7}}`；关闭：`"interval_days": "off"` |
| 自动清理 | 开 | `"cleanup": {"enabled": false}` 关闭 |
| 原始文件保留天数 | 45 天 | `"raw_files": {"retention_days": 60}`；关闭：`"retention_days": "off"` |
| 解析并发 | 4 | `"workers": 4`，1–8 |
| 多久没有成功的运行算问题 | 48 小时 | `"stale_after_hours": 48`。成功指运行跑完，并且没有任何失败或被跳过的集群 |

每一项的取值范围见[配置指南](configuration-guide.md#想让每天自动运行)。写错键名或取值时命令直接拒绝，不写入任何数据。

## 二、接收目录和齐全标记

每个来源一个接收目录，日志文件保持源端的原名放进去：

```text
/data/sql-apm/inbox/120/
  gpdb-2026-10-09_000000.csv
  gpdb-2026-10-09_000000.csv.1
  gpdb-2026-10-09_000000.csv.2
  2026-10-09.complete            <- 齐全标记
```

- **文件属于哪一天**看文件名里的日期：`gpdb-年-月-日_时分秒.csv`，后面可以带 `.1`、`.2` 这样的数字。一天有几个文件都可以。
- **齐全标记**是一个名为 `年-月-日.complete` 的空文件，表示“这一天的文件已经全部拷完”。文件拷完之后再放：

  ```bash
  touch /data/sql-apm/inbox/120/2026-10-09.complete
  ```

- **只有放了标记的日期才处理。** 没有标记的文件不读取、不登记、不移动，只在运行记录里提一句。
- **标记的日期必须早于今天**（服务器本地日期）。给今天或以后的日期放了标记，那一天不处理并列为待处理问题；
  发现后先撤掉标记，等那一天结束、文件拷全之后再放。过了那一天它就按普通的标记处理，目录里如果还是没拷完的文件，
  会被照样导入，之后完整的文件会被判为冲突。
- **清单冻结。** 命令第一次处理某一天时，把当时目录里这一天的全部文件登记为这一天的批次，清单从此不变。
  之后这一天再多出文件、少了文件或文件内容变了，会被报告为这一天的冲突，不会并入。内容按导入时保存的校验值核对，
  所以大小不变的改动、换成另一个同名文件也算变了。**放了标记的日期，它的文件就不要再动。**
- **其他文件**（名字既不是日志文件也不是标记）不处理，只记录个数和名字。子目录不看；符号链接一律当作其他文件，不跟随。

标记可以由人放，也可以由传输脚本放，效果相同。放下之后可以等下一次定时运行，也可以立即手工执行。

## 三、手工运行

```bash
export SQL_APM_DSN="host=/path/to/socket port=5432 dbname=sql_apm user=sql_apm"
export PGPASSFILE=/path/to/pgpass
python -m sql_apm daily run --config /data/sql-apm/config/daily.json
```

- 连接方式与其他命令相同，不把密码写进命令或配置。
- 输出是逐行的 JSON，只含原因码、计数、日期、文件名和标识，不含 SQL 原文、库名和用户名。最后一行给出本次运行的结果。
- 同一时间只允许一个每日运行。已有一个在运行时，第二个立即退出，输出 `daily_run_active`，不改动任何数据。
- 某个集群正被别的任务占用（例如有人在手工执行 `full`）时，本次运行跳过它并记录，不等待，这个集群的任何东西都不动，包括不删除它的原始文件；下一次运行补上。
- 用 Ctrl-C 或 `kill` 停止时，命令停下当前步骤，把这次运行记为“被中止”，以 130 退出。命令正在等一条很长的语句或等锁时也一样，通常一秒之内停下。下一次运行照常接上：已导入成功的文件不重复导入。

| 退出码 | 含义 |
| --- | --- |
| 0 | 全部完成，没有失败。包括没有可做的事、整窗没有有效样本所以版本未更新、清理因为拿不到锁留到下次 |
| 1 | 有日期导入失败或冲突、构建或发布失败、有集群被跳过、清理或删除文件出错；或配置有误、数据库连不上 |
| 2 | 命令行参数错误 |
| 130 | 被中止 |

## 四、首批多天

首批（例如 30 天）与日常走同一条路：把这些天的文件都放进接收目录，逐天放标记，然后手工执行一次命令。
它逐天导入，最后只构建一次，截止日是最新的那一天。手工执行没有运行时间上限。

```bash
for day in 2026-09-10 2026-09-11 2026-09-12; do touch /data/sql-apm/inbox/120/$day.complete; done
python -m sql_apm daily run --config /data/sql-apm/config/daily.json
```

注意原始文件保留天数是按**数据日期**算的：导入一天早于“今天减保留天数”的旧日志时，它的文件在导入成功的同一次运行里就会被删除。
需要保留这些文件时，先把 `raw_files.retention_days` 调大或设为 `"off"`。

## 五、查看运行状态

**命令行。** 只读，不占用集群，任何时候都可以执行：

```bash
python -m sql_apm daily status --limit 10
```

输出一个 JSON：`clusters`（每个集群的最新已导入日期、当前版本的截止日和发布时间、上次运行在该集群的结果、待处理问题数）、
`problems`（当前的待处理问题）、`runs`（最近若干次运行，每次运行里每个集群导入了哪些天、是否构建发布、清理和删除文件的结果、各步骤耗时）、
`nonconforming_files`（最近一次运行在接收目录里看到的其他文件）。

**看板。** Grafana 的 MPP 文件夹里有“运行状态”看板，“SQL 检索”和“SQL 列表”页面右上角有到它的链接。它只展示，
不能在页面上触发导入、构建或清理；每分钟自动刷新。内容与命令行相同：

- 最上面四个数：上次运行的开始时间、结果、上次成功的运行的时间、待处理问题数。“成功”指跑完并且没有任何失败或被跳过的集群，所以“完成，有失败”的运行不会更新第三个数。
- **各集群现状**：每个集群一行。
- **待处理问题列表**：每一条带“怎样处理”。没有问题时显示“（没有待处理的问题）”。
- **最近的运行记录**：一行是一次运行里的一个集群。

运行结果的写法：**完成**（都处理完，没有失败）、**完成，有失败**（跑完了，但有失败的日期、失败的构建、清理或删除出错，或被跳过的集群）、
**被中止**（收到停止信号，包括定时启动的运行超过了最长运行时间）、**未正常结束**（进程被强制终止或机器断电）。

## 六、待处理问题怎样处理

每一类问题取最近一次真正做到那一步的运行所记录的。一次运行跳过了某个集群、或中途停下，它没有做到的步骤不会让问题从列表里消失；
问题解决之后，下一次做到那一步的运行不再记录它，列表里随之消失。

| 问题 | 含义 | 怎样处理 |
| --- | --- | --- |
| 导入失败或有冲突的日期 | 这一天的批次没有整批导入成功，或导入之后目录里它的文件有增减、内容有变化。只影响这一天，后面的日期和构建照常进行 | 按“说明”一栏的原因处理（见文末原因码）。下一次运行自动重试。多出来或变了的文件移出接收目录；确实需要它的数据时，用 `import` 以人工批次导入 |
| 有文件但没有齐全标记 | 这一天的文件在目录里，但没有标记，所以没有处理。它不妨碍别的日期 | 确认文件齐全后放上标记；不需要这些文件就移走 |
| 有齐全标记但没有文件 | 有标记，目录里却没有这一天的文件 | 把文件拷进来，或删除这个标记 |
| 标记日期不早于今天 | 给今天或以后的日期放了标记 | 撤掉标记；那一天结束、文件拷全之后再放 |
| 等待清理的月份 | 过期月份因为拿不到锁没有清理（通常是当时有查询在读统计表），或清理没有做完 | 不用处理，下一次运行会再试。长期不消失时看是否有会话一直占着统计表 |
| 上次运行跳过了这个集群 | 最近一次轮到这个集群时，它正被别的任务占用，所以它的导入、构建、清理和删除都没有做 | 不用处理，下一次运行补上。可用 `status --cluster 集群` 看当时的任务 |
| 构建或发布尚未成功 | 构建、检查或发布失败，当前版本保持不变 | 下一次运行会重试。用 `status --cluster 集群` 看未发布的原因 |
| 上次运行没有正常结束 | 最近一次运行被中止或被强制终止 | 下一次运行会接上；想马上补上就手工执行一次 |
| 太久没有成功的运行 | 超过 `stale_after_hours` 没有一次成功的运行；跑完但有失败、只是跳过了集群、被中止的运行都不算成功。从来没有成功过时从第一次运行算起 | 先处理列表里的其他问题；没有别的问题时看定时器是否启用、数据库是否在运行，然后手工执行一次 |

整窗没有有效样本时不更新版本，这不算失败，也不列为问题；条件仍然成立，所以之后每次运行都会再构建一次，直到有了样本。

## 七、定时启动

定时启动是可选的。不装定时器时，手工或用别的方式执行同一条命令，效果相同。

**生成单元文件**（不需要 root，可以重复执行）：

```bash
python scripts/daily/install.py --output /tmp/sql-apm-units \
  --config /data/sql-apm/config/daily.json \
  --dsn "host=/path/to/socket port=5432 dbname=sql_apm user=sql_apm" --passfile /path/to/pgpass \
  --user sfmon --at 17:00
```

它生成 `sql-apm-daily.service` 和 `sql-apm-daily.timer` 两个文件。常用参数：`--at HH:MM` 是每天启动的时刻（服务器本地时间），
可以重复给出多个，默认 17:00；`--max-hours` 是定时启动的运行最长多少小时，默认 12；`--user` 是运行它的系统用户，
用项目用户；`--fetch-config` 见下一节。用项目的解释器执行它。

单元文件对本机所有用户可读，所以**连接串里不能有密码**：关键字形式的 `password=`、URI 形式的“用户:密码@主机”和 `?password=`
（包括百分号编码的写法）都会被拒绝，不生成任何文件，报错里也不重复连接串。密码放在 `--passfile` 指向的文件里。

**安装和启用**（需要 root）：

```bash
sudo cp /tmp/sql-apm-units/sql-apm-daily.service /tmp/sql-apm-units/sql-apm-daily.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now sql-apm-daily.timer
systemctl list-timers sql-apm-daily.timer        # 下一次启动的时间
```

**停用**：`sudo systemctl disable --now sql-apm-daily.timer`。**改时刻或上限**：用新的参数重新生成，覆盖两个文件，
再执行 `sudo systemctl daemon-reload` 和 `sudo systemctl restart sql-apm-daily.timer`。**看某一次的输出**：
`journalctl -u sql-apm-daily.service`。

定时器的行为：

- 到时刻启动一次每日运行，运行记录里的启动方式为“定时”。
- **上一次还没结束时不会同时启动第二个。** 到点时上一次还在运行，systemd 会等它结束后立即补跑一次；这一次通常没有新的事可做。
- **机器停机错过的那一次，开机后补跑一次。** 补跑需要数据库已经在运行：现在的安装方式里 PostgreSQL 由人工启动，
  所以**服务器重启后要先启动数据库**。否则补跑会因为连不上数据库而失败，数据库里也不会有这次运行的记录
  （系统日志里是 `database_unavailable`），积压的日期要等下一次运行处理；数据不会丢。
- **定时启动的运行超过最长时间会被停止。** systemd 发停止信号，命令停下当前步骤（正在执行一条很长的语句或等锁时也一样），
  把这次运行记为“被中止”，以 130 退出，集群占用随即释放，下一次运行接着做。手工执行的命令不受这个上限限制。
  `sudo systemctl stop sql-apm-daily.service` 停止一次正在进行的运行，效果相同。
- `systemctl status sql-apm-daily.service` 显示 failed 表示那次运行的退出码是 1（见第三节）或因为超过最长时间被停止，
  不影响下一次定时启动。

## 八、传输脚本

`daily/fetch-logs.sh` 在基线服务器上运行，用 scp 从 MPP 的 master 把已经结束的日期的日志拉到接收目录，
整天到齐后放齐全标记。它是可选的：不用它时，手工拷贝并放标记，其余功能完全一样。

**前提。**

- 基线服务器上运行它的用户能用 SSH 密钥**免密登录**源端主机。脚本只用密钥登录，不存放也不询问密码；
  没有配置免密登录时立即报错退出。
- 源端主机的主机密钥已经在该用户的 `known_hosts` 里。第一次先手工 `ssh 账号@主机` 登录一次并核对、接受主机密钥；
  脚本不会自动接受未知或变化了的主机密钥。
- **源端账号的最小权限**：能登录，能列出并读取日志目录里的文件。脚本对源端只执行 `find`（列文件和大小）和 scp（读文件），
  不写、不删、不改源端的任何东西，同一时间只开一个连接。

**配置。** 一个文本文件，一行一个来源，字段用空白隔开（参见 `daily/fetch-logs.conf.example`）：

```text
# 名称   登录账号@主机   源端日志目录                  本地接收目录                 [SSH 端口]
mpp-119  gpadmin@mdw-119  /data/master/gpseg-1/pg_log  /data/sql-apm/inbox/119
mpp-120  gpadmin@mdw-120  /data/master/gpseg-1/pg_log  /data/sql-apm/inbox/120  22
```

**运行。**

```bash
daily/fetch-logs.sh --config /data/sql-apm/config/fetch-logs.conf                       # 昨天，并补上最近 7 天里还没有标记的日期
daily/fetch-logs.sh --config /data/sql-apm/config/fetch-logs.conf --date 2026-10-08     # 指定某一天
daily/fetch-logs.sh --config /data/sql-apm/config/fetch-logs.conf --from 2026-09-10 --to 2026-10-08   # 一段日期
```

- 只取今天之前的日期；今天还在写的文件不取。
- 每个文件先用临时名字（`.文件名.part`）拷贝，核对大小与源端一致后才改成正式名字。那一天的文件全部到齐、
  并且源端这一天的文件清单在拷贝前后没有变化，才放齐全标记。任何一步失败都不放标记，下一次运行会重试。
- 源端没有某一天的文件时不放标记，也不算失败。本地已经有、大小相同的文件不重复拷贝。
- **已经有齐全标记的日期不再拉取，也不改动**，不论是自动补拉、`--date` 还是 `--from`／`--to`：它的文件可能已经导入，
  再动就会被判为冲突。点名要这样的日期时，脚本只比较源端现在的文件清单（名字和大小）与本地是否一致：一致时输出
  `state=already_complete`；不一致时输出 `reason=marked_day_differs_from_source` 并以 1 退出，本地的文件和标记都原样不动。
  这一天还没有导入、确实要重新取时，先人工删除它的标记和文件再拉；已经导入的日期不要重新取。
- 退出码：0 全部到齐或无文件可取；1 有日期或来源失败；2 参数或配置错误。
- `--backfill-days N` 改变自动补拉的天数（默认 7）。原始文件保留天数不要设得比它小，否则已经删除的日期会被再次拉取。

**与定时器衔接。** 生成单元文件时加上 `--fetch-config /data/sql-apm/config/fetch-logs.conf`，同一个定时任务就先拉取、再执行每日运行，
只需要设一个时刻。拉取失败不妨碍每日运行处理已经有标记的日期。

## 九、调整

- **不想每天都出新版本**：把 `build.interval_days` 调大（例如 7），或设为 `"off"` 之后用 `rebuild` 人工构建。导入仍然每天做，
  Grafana 里的执行历史保持最新。
- **版本结果的保留月数**：改训练配置的 `retention`。**调小之前先人工预览一次**
  （`python -m sql_apm cleanup --cluster 集群 --training-config FILE`，不带 `--execute`），因为自动清理没有预览这一步，
  调小后下一次每日运行就会删除，删除的结果不能恢复。
- **原始文件的保留天数**：改 `raw_files.retention_days`。调小后下一次运行就会删除更早的文件。
- **每天的时刻、最长运行时间**：见第七节。
- **进程被强制终止后多久释放集群占用**：环境变量 `SQL_APM_CONNECTION_CHECK_SECONDS`，默认 10 秒，对所有命令生效；
  单元文件里由 `--check-seconds` 写入。

## 十、哪些内容会被自动删除

| 内容 | 什么时候删 | 怎样关闭 | 删了之后 |
| --- | --- | --- | --- |
| 过期月份的版本统计结果 | 构建月份早于“当月和之前 N 个整月”（N 是训练配置的保留月数，默认 2）；当前版本所在的月份受保护 | `"cleanup": {"enabled": false}` | 不能恢复。版本、构建和发布的记录保留，历史里标为已清理 |
| 接收目录里的原始日志文件和它们的齐全标记 | 那一天已整批导入成功、日期早于“今天减保留天数”（默认 45 天），并且删除前把那一天的每个文件重读一遍、确认内容与导入时相同 | `"raw_files": {"retention_days": "off"}` | 本机不再有副本，依靠生产上的日志备份 |

永远不会被自动删除的：导入失败或有冲突的日期的文件、没有标记的文件、不属于批次的文件、接收目录之外的任何文件。
数据库里的 SQL 原文和执行明细不清理。删除前命令会确认文件确实位于接收目录之内。

集群正被别的任务占用时不删除它的原始文件。删除中途被打断（删除出错、被停止、进程被强制终止）时，已经删掉的文件有记录，
下一次运行接着删完那一天，不会把“文件少了”当成冲突；打断之后新出现或内容变了的文件仍然会被报告，那一天不再继续删。
各次运行记录里的文件数和字节数加起来，等于实际删除的数量。

## 需要知道的边界

- 已导入的日期的文件有没有变化按内容判断：与导入时保存的校验值（SHA-256）相同才算没变。为了不每天重读全部文件，文件的设备号、inode、大小、修改时间和状态改变时间都与上次核对时相同的，视为没动过、不重读；任何一个变了就重读。删除之前一律重读。本地样本上重读约 1.4 秒／GiB。
- 构建间隔按数据日期计算，与哪一天运行无关。补导一个较早的日期不会触发构建，它包含在之后的下一次构建里。
- “今天”和原始文件保留天数按服务器本地日期；版本结果的月份按数据库的北京时间。
- 每日运行里每一步调用的就是对应人工命令的同一段程序，导入、训练判定、统计、发布检查和清理的规则没有变化。
- 连接存活检查在开发机的 PostgreSQL 17.10 上验证；目标机上的验证见 #52。

## 原因码

“说明”一栏常见的原因：

| 原因码 | 说明 |
| --- | --- |
| `file_unreadable` | 文件读不了（权限或文件不存在） |
| `file_changed_during_read` | 读取期间文件在变化，通常是文件还没拷完 |
| `file_processing_failed` | 文件内容处理失败 |
| `files_changed_after_import` | 这一天导入成功之后，目录里它的文件有增减，或内容与导入时不同（大小不变的改动、换成另一个同名文件也算）。把多出来或变了的文件移出接收目录；被改的文件换回导入时的那一份后，下一次运行自动恢复正常 |
| `batch_manifest_changed` | 这一天第一次登记之后、导入成功之前，文件清单变了（多了、少了文件）。把清单恢复成第一次登记时的样子即可重试；做不到时，把这一天的文件和标记移出接收目录，用 `import` 以人工批次导入 |
| `origin_content_changed` | 同名文件的内容与已导入的不同 |
| `record_edge_overlap` | 文件内容与已导入的文件重叠 |
| `cluster_busy` | 集群正被其他任务占用 |
| `cleanup_lock_timeout` | 清理拿不到锁，月份保持原样 |
| `cleanup_groups_pending` | 统计结果已删除，分组行还没删完，下次继续 |
| `publication_checks_failed` | 发布检查没有通过 |
| `raw_delete_failed` | 删除原始文件时出错（权限等） |
| `operator_interrupt` | 运行被停止（Ctrl-C、`kill`、`systemctl stop` 或超过最长运行时间） |
| `daily_run_active` | 已有一个每日运行在进行 |
| `database_unavailable` | 连不上数据库 |
