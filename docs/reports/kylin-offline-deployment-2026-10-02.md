# Kylin V10 SP2 离线部署验证（2026-10-02）

[Issue #31](https://github.com/shenxg13/sql-apm/issues/31) 的实施证据。
[操作手册](../runbooks/kylin-offline-deployment.md)、
[用户记录模板](../runbooks/kylin-validation-record.md)与
[机器记录](data/kylin-offline-deployment-2026-10-02.json)分别保存步骤、人工结果和脱敏实测。
本报告不代表生产部署，也不代替用户恢复快照后的独立执行。

## 输入与适用性

程序包固定为包含 #29 的 main `6451d140d44f4e06cc34862c3e5aff7593d7afeb`。
产品代码和规则未改；唯一已有验证代码改动为 verify_publication.py 的 --pg-bin，
默认路径保持开发机原值。部署辅助文件与手册作为有独立摘要的 support 交付。

[Alma 对照](data/kylin-alma-baseline-2026-10-02.json)来自
[#29 R2 最终 head 重放](https://github.com/shenxg13/sql-apm/pull/30#issuecomment-5939592275)。
其产品文件摘要与 main 合并树逐项相同；保存原机器记录摘要及九任务全部可比较计数。
没有拿早期含合成排除时段的统计报告作等值基准。

固定 55 个日志共 15,816,193,813 字节，仅传到已授权演练机的 /data/sql-apm/logs；
目标机逐项摘要与源端清单一致。程序包、RPM、日志、数据库和密码文件均未进入 Git。

## 观察与部署验证

以下为 observed：演练系统 Kylin V10 SP2 Build09、x86_64、glibc 2.28，
8 vCPU、约 14 GiB 内存，/data 为约 190 GiB XFS；免密 sudo 可用。
虚拟机快照已创建由用户提供，SSH 检查不证明快照可恢复。

以下为 measured／verified：

| 项目 | 实际结果 |
| --- | --- |

## 九任务与资源

串行执行 119 首批、三个日批、一次重建，再执行 120 首批及三个日批。
每步通过实际 CLI，立即查询 status/history，核对窗口、结果及前驱链，并比较 Alma 计数。
阶段耗时、数据库字节和文件系统占用由机器记录保存；总耗时包含 CLI 与后续核对。
这些为 measured，不设性能门槛；磁盘占用包含同一数据盘上的其他演练材料，不等同数据库大小。

首次四进程试跑的首个任务（119 首批，截止 2026-07-28）发布成功，但 Alma 等值检查失败，
辅助执行器退出 1 并停止后续八个任务。status/history 的当前版本、窗口和前驱链核对通过，
六项发布检查通过不等于跨平台计数一致；该次试跑未通过 K8／K9／K10。

### 用户要求的 SSD 迁移暂停

用户确认虚拟磁盘底层为机械盘（user-reported），并要求先安全停止再迁移到 SSD。
暂停前 20.098 秒只读采样显示：CPU 空闲 87.91%、I/O 等待 10.71%；
Python 与 PostgreSQL 分别消耗单核 3.83% 和 5.22%。数据盘读取约 45.08 次／秒、
平均读取延迟 41.842 毫秒、忙碌率 93.54%；20 次数据库活动采样均为 DataFileRead，
分布于指纹插入、执行记录与 SQL 证据 COPY、缓存查询等操作。
这支持“当前导入主要受存储读取延迟限制”的推断，不证明 SSD 的实际改善幅度。
未修改产品代码、并发数或数据库参数，也没有运行额外磁盘压测。

先暂停串行父 Shell，向当前 CLI 发送 SIGINT；程序将 120/1 任务记为
`interrupted/import/operator_interrupt`，没有发布该日批。运行任务数为 0，
119 保留 5 个版本、120 保留 1 个版本；120 导入尝试为 13 次成功、1 次人工中断。
保存两集群 status/history 后正常关闭 PostgreSQL，控制文件状态确认为 `shut down`，
项目进程和 postmaster.pid 均已消失。48 个记录文件已备份到开发机 0700 忽略目录，
压缩包可完整读取，摘要见机器记录；目标机原件未删除。

迁移后从 120/1 恢复。保留中断证据；恢复执行器须区分额外的中断尝试与基准中的成功
导入次数，不能删除中断记录或直接覆盖旧日志来强行匹配。剩余三项在实际通过前保持未完成。

## 尚未完成与失败边界

- 跨机正确密码测试曾因缺少明确凭据导出授权被自动审批拒绝。
  用户随后明确允许临时复制到开发机 /tmp 的 0700 目录／0600 文件；
  TCP 只读查询核对项目账号、库和 PG17.10 全部成功，退出后临时文件及目录已删除。
  密码未显示、未写入报告或 Git。用户随后确认 pgAdmin 连接及只读验证成功，
  此部分标记为 user-reported；结合实施方的 TCP 正误密码验证，K6a 已完成。
- 超时诊断曾因返回 SQL 长度／统计元数据被自动审批拒绝；用户明确授权上述
  最多 8 条、原机回放、仅返回统计的范围后才执行，未导出 SQL 正文。
- 自动审批曾拒绝递归取回整个 records 目录；随后仅导出已核对字段的版本、模块、
  测试项数、权限与耗时摘要。用户后来明确授权内网敏感文件传输，失败任务记录另行备份到
  本地 0700、Git 忽略目录；目标机原件保留，提交报告仍只使用核对后的摘要。
- 用户恢复快照后的 yum 源安装及两项编译、独立完整执行尚未完成；
  对应 K3a、K11 不能标记全部通过。
- 生产内网源、不同初始系统上的 RPM 完整性、120 三十天首批成本和 aarch64 均未验证。
- 九任务之后的并行重建为可选，本次尚未执行；不据此增加已验证场景。
