# v1.0.0 密码首尾空白整改验证

本次只处理 [PR #60 的 R1 阻断 F-59-60-R1-001](https://github.com/shenxg13/sql-apm/pull/60#issuecomment-6146826478)，
对应 Issue #59 的 M8 及受影响的安装路径。原密码契约不变：数据库接受非空单行密码，
Grafana 保留固定上游至少 4 字符的限制，项目不增加字符规则。

## 原因与修复

Grafana 的 [file provider](https://grafana.com/docs/grafana/latest/setup-grafana/configure-grafana/#file-provider)
会去掉首尾空白，导致管理员初始密码被改变、只读数据源与数据库实际密码不一致。
输入文件和 pgpass 原样保存密码不能保证最终消费者使用原值。

`scripts/grafana/install.py start` 在每次启动时读取受保护文件，再以 `execve` 启动固定 Grafana。
管理员密码通过文件 provider 最后展开，同时精确补回其删除的 Unicode 空白；密码中的变量或 provider
样式文本不再被二次解释。数据源使用最终一次展开的 `$SQL_APM_GRAFANA_DB_PASSWORD`，
遵循 [Grafana provisioning 的变量展开规则](https://grafana.com/docs/grafana/latest/administration/provisioning/#use-environment-variables)。
生成的 systemd 服务与开发机安装入口都使用同一启动入口。

密码仍保存在 0600 文件，不进入命令行参数、生成的配置或日志。只读数据库密码在 Grafana 进程环境中，
其读取边界为同一执行用户和 root；没有写入系统级环境文件。启动入口保持 Grafana 为 systemd 主进程，
轮换后的密码由下一次启动重新读取。

## 实测

目标机使用固定候选 `b8fa0d337f56698d51dc8bbd716e64dfc87e109c` 的程序包和独立验收包，先核对包摘要及清单。
复用原先唯一的 Python／PostgreSQL 运行时及固定 Grafana 13.2.3，在独立目录、私有数据库和随机本机端口验证。
全部密码与 SQL 为合成样本，未修改用户已验收安装中的账号或数据。

开发机和 Kylin 验证机各完成以下五组真实认证回归（measured）：

| 阶段 | 输入 | 检查结果 |
| --- | --- | --- |
| 首次安装 | 首尾空格、制表符，含冒号与反斜杠 | 四账号原值认证、Grafana 表单登录、数据源与指纹服务通过 |
| 轮换 1 | 首尾制表符 | 原值成功，去掉首尾空白的错误值失败 |
| 轮换 2 | 首尾空格，含变量／provider 样式文本及引号 | 原值成功，特殊文本保持字面值 |
| 轮换 3 | Grafana 4 字符、数据库单字符 | 原值认证通过，数据库冒号密码正确转义 |
| 轮换 4 | 完全由空格和制表符组成的 4 字符密码 | 四账号原值认证、表单登录及服务认证通过 |

每组还验证两个数据库角色、只读拒写、凭据文件权限和指纹检索请求；有首尾空白的组验证去空白值被拒绝。
Grafana 上游创建查看账号时拒绝 1–3 字符的检查通过。生成配置及日志中未发现所用非空白长合成密码。
这些检查由验收包中的 `scripts/grafana/verify_credentials.py` 提供，未加入生产程序入口。

Kylin 上另用临时 systemd 服务运行生成的 `ExecStart`，管理员登录与数据源认证通过，主 PID 的可执行文件为 Grafana，
命令行参数不含合成密码。临时服务、私有 PostgreSQL 和指纹进程全部停止。
原安装的三个服务 PID 与状态未变、每日定时器仍未运行；RPM 摘要及运行时 5,821 项清单核对一致。
合成测试证据已复制回开发机并核对归档摘要，详细路径和机器记录保留本地，不公开。

开发机 104 个普通测试、12 个安装工具测试、37 个制包测试、7 个 Grafana 工具测试通过；
文档自动检查和完整离线 Harness 通过。普通测试中对旧数据源模板的断言已随修复更新。
