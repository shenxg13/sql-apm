# 日志导入、来源与异常处理

## Summary

保存完整文件导入、来源登记、安全重试及按问题影响范围处理的要求。
修改导入、文件识别、批次完整性或导入诊断时阅读。

适用范围：以下为首期 HashData 契约；设计后续来源接入时，参照
[多类型系统接入约束](../decisions/project-scope.md#已确认的多类型系统接入扩展约束)。

## Contracts

### 已确认的日志获取方式

- 确认日期：2026-09-22。
- 来源：用户明确要求首期手动将 SQL 日志文件拷贝到基线服务器，后续再通过
  简单脚本定时调用 SCP，每天传输一次。用户原话中的“极限服务器”按上下文
  理解为“基线服务器”。
- 来源状态：current；已确认获取方式及阶段安排，自动传输尚未实现。
- 首期由用户手动拷贝日志文件，基线程序从基线服务器上的本地文件导入数据；
  不引入任何流式日志读取或采集组件。
- 后续通过简单脚本和定时任务，每天一次将日志文件通过 SCP 拷贝到基线服务器。
- 具体源目录、接收目录、传输任务执行端、调度时刻及导入触发方式留待实现前确认。
  当前不配置 SCP 脚本或定时任务。

### 已确认的集群标识与日志来源映射

- 确认日期：2026-09-25。
- 来源：用户对人工登记固定集群标识及日志来源映射、导入时选择已登记来源、
  目录或文件改名沿用标识、Master 来源变化后人工确认归属，以及映射不明确时
  先补充信息再导入的建议回复“确认”。
- 来源状态：current；标识与归属原则已确认，#18 已实现登记配置与只导入入口。
- 人工维护固定的计算集群标识及“日志来源 → 集群”映射。每个已登记日志来源
  明确对应所属集群；导入时显式选择已登记的日志来源，再按映射确定集群。
- 集群标识用于既有基线分组和按集群管理版本；日志来源标识用于文件追溯、
  同一来源内重复导入识别和日志关联，不新增为基线 GROUP BY 维度。
- 文件或目录改名不改变其来源和集群标识；不因路径、文件名变化自动创建新
  集群或改变既有分组归属。内容相同且此前成功导入的跳过规则仍按同一来源判断。
- Master 来源变化时，由人工登记或确认日志来源的归属；确认为同一逻辑集群
  时沿用原集群标识，不把每次来源变化自动当作新集群，也不自动推断不同来源
  必属同一集群。既有日志关联的可靠性要求仍适用。
- 来源未登记、来源不明确或映射不明确的文件先不导入，提示补充信息；完善
  归属后再按已有完整文件、批次和导入资格规则处理。
- `hashdata-119`、`119-master-a` 仅是讨论中的命名示例，不代表已经创建登记项；
  来源映射通过本地配置文件维护，JSON 格式、命令与持久化见本页首期实现。
  本条不改变现有安全重试要求；
  变更及部分重叠文件的首期处理见下文。

### 完整文件导入、重复处理与重试

- 确认日期：2026-09-22。
- 来源：用户对“首期仅导入已经结束写入、复制完成的完整日志文件；已成功导入
  的相同文件再次提交时跳过；导入中断后允许安全重试”的建议回复“确认”。
- 来源状态：current；已确认导入边界及重复处理原则；#18 已实现文件事务、重复跳过与中断恢复。
- 首期按已结束写入且已复制完成的完整日志文件导入。
- 同一日志来源下，内容相同且已经成功导入的文件再次提交时跳过；文件改名不
  应导致相同内容被重复计入样本。
- 导入中断后允许重新执行；同一文件的重复导入或失败重试，不应使此前已经
  处理的执行记录重复计数。未完成的导入不能当作已成功导入而直接跳过。
- 当天批次尚未完整导入时，不发布新的基线；完整导入后再按已确认流程构建和
  发布新版本。
- 去重针对日志重复导入，不按 SQL 文本或结构指纹合并真实执行；同一 SQL 真实
  执行 100 次，仍应记录为 100 次执行，随后按训练资格筛选样本。
- 同一文件后续追加或变更、不同文件之间内容部分重叠，按下述已确认的首期
  冲突处理规则执行；不将完整文件去重视为已经覆盖这些情况。
- 集群与日志来源采用上节已确认的人工登记及映射规则；文件标识、内容一致性
  判定和中断恢复的具体实现仍待落实。批次完整性采用下述已确认原则，来源登记
  配置和文件清单格式仍待落实。本次不固定数据库事务或断点恢复方案。

关联条款：[已确认的同集群任务串行与忙时处理](baseline-versions.md#已确认的同集群任务串行与忙时处理)；[已确认的五类计时统一版本与发布边界](baseline-versions.md#已确认的五类计时统一版本与发布边界)。

### 已确认的变更及部分重叠文件处理

- 确认日期：2026-09-25。
- 来源：用户对首期暂不自动合并追加／修改或部分重叠文件、可靠识别冲突后暂停
  受影响文件并阻止该集群本批次发布、待人工核对的建议，选择“暂不自动合并，
  冲突人工核对”。
- 来源状态：current；已确认处理边界；#18 已实现内容身份、人工原文件标识与边缘重叠检测，覆盖限制见首期实现。
- 首期不自动合并追加／修改文件，也不自动合并不同文件中的部分重叠内容。
  对能可靠确认是已导入源文件变更，或不同文件重复携带部分同源日志的情况，
  记录原因、来源及判定依据，暂停受影响文件，待人工核对；不自动覆盖旧数据
  或提取增量。
- 冲突未解决时，该集群本批次不发布新基线，保留原生效版本；受影响文件不能
  当作导入成功或有效重复跳过来满足批次完整性。其他集群仍按自身批次和检查
  结果独立处理。
- 同一来源下内容完全相同、且此前已经成功导入的文件仍按既定规则跳过；原文件
  内容未变化的失败或中断重试继续安全支持，不因重试本身视为变更或重叠冲突。
- 文件名相同、日志时间范围相交或 SQL 文本相同，本身不足以判定文件变更或
  同源日志重复。真实重复执行仍分别保留，不能按 SQL 或结构指纹去重执行记录；
  SQL 原文存储的精确内容去重也不替代日志记录的重复识别。
- 具体文件身份、冲突识别方法与覆盖范围，以及人工核对后的恢复或重新提交流程
  仍待实施前落实和验证；此决定不保证已经能发现所有变更或部分重叠内容。

关联条款：[已确认的同集群任务串行与忙时处理](baseline-versions.md#已确认的同集群任务串行与忙时处理)；[已确认的首期基线发布检查](baseline-versions.md#已确认的首期基线发布检查)。

### 首期导入批次的完整性判定

- 确认日期：2026-09-23。
- 来源：用户对“人工确认文件齐全，程序核对处理完成”的首期批次完整性方案
  回复“确认”。
- 来源状态：current；已确认判定原则；#18 已实现入口、冻结清单与批次完成核对，构建发布尚未交付。
- 每次手动导入时，由用户指定日志来源、覆盖日期及本批次文件，并确认所需
  文件已拷齐；文件仍须满足已结束写入且复制完成的既有要求。导入批次及相应
  构建、发布按计算集群独立管理，见下述已确认的版本范围。
- 程序记录本批次文件清单。只有清单内文件全部完成导入，或按同一来源下相同
  内容此前已成功导入的规则跳过后，才进入基线构建；失败或未完成的文件不能
  作为已完成项，也不能当作成功的重复文件跳过。
- 文件齐全依赖人工确认；程序不能仅凭本地文件名、文件是否存在或最后一条
  日志的时间，断言源端没有漏拷文件。覆盖日期的人工声明不等同于独立验证。
- 已确认的记录级问题隔离、文件级失败处理及基线发布检查继续适用；完成文件
  清单的处理不代表所有记录都具备训练资格，也不绕过后续质量检查。
- 首期操作入口已确认采用命令行，来源映射和批次文件清单通过本地配置文件
  维护。具体文件格式、命令参数、文件标识及后续 SCP 自动化的衔接仍待落实；
  本次不固定其存储模型或新增自动传输功能。

关联条款：[已确认的首期操作入口](operator-cli.md#已确认的首期操作入口)；[已确认的首期基线发布检查](baseline-versions.md#已确认的首期基线发布检查)。

### 导入异常的处理

- 确认日期：2026-09-22。
- 来源：在询问可可靠定位的问题记录是否排除受影响样本后继续处理、文件损坏
  导致记录边界不可靠时是否导入失败并阻止本批次发布新基线时，用户选择
  “按问题影响范围处理（推荐）”。
- 来源状态：current；已确认异常处理原则；#18 已实现记录隔离和文件／批次状态。

| 情况 | 处理原则 |
| --- | --- |
| 个别执行缺少关键信息、无法生成可靠指纹等，且能可靠确定受影响范围 | 记录原因，相关执行暂不参与训练，继续处理其他可靠记录 |
| 文件结构损坏或不完整，无法可靠确定记录边界 | 该文件导入失败，本批次不发布新基线 |
| 日志正常记录 SQL 执行报错 | 正常解析，按已确认规则排除出耗时训练，不作为导入程序失败 |

- 记录级问题的处理以能可靠确定受影响范围为前提；不能将排除一条日志记录
  自动等同于已排除该问题对关联执行的全部影响。
- 每次导入汇总问题数量、原因及文件中的定位信息，供后续检查和修复。问题记录
  数不直接等同于被排除的 SQL 执行次数。
- 能够完成导入的批次仍需通过基线发布检查；首期采用下述已确认的完整性与
  计算一致性检查，暂不增加覆盖率、有效样本比例或相对旧版波动的发布阈值。
  具体检查实现仍待落实。
- 本次确认不改变失败导入可安全重试、未完成导入不能视为成功重复文件的规则。
  指纹生成失败采用下节已确认规则；问题数据的存储与留存、日志到执行的关联
  及指纹生成的具体实现继续另行落实。

关联条款：[已确认的训练样本基本资格](../contracts/training-eligibility.md#已确认的训练样本基本资格)；[已确认的首期基线发布检查](baseline-versions.md#已确认的首期基线发布检查)。

### 已确认的指纹生成失败处理

- 确认日期：2026-09-25。
- 来源：用户对无法可靠生成结构指纹时暂不训练、不自动降级为原文哈希或简单
  文本指纹、批次不截取可解析部分使用整批耗时，以及继续按问题影响范围处理
  的建议回复“确认”。
- 来源状态：current；回退边界已确认，结构与近似指纹接口及 #18 导入已有实现，样本筛选尚未交付。
- 首期依据已确认的归一化规则生成结构指纹；若最终无法可靠生成，不自动改用
  原文哈希、简单去空格后的文本标识或其他简单文本指纹继续建立正常基线。
- 2026-09-27 用户追加确认[观察用近似指纹](../contracts/sql-fingerprints.md#已确认的观察用近似指纹)：
  可对边界能确定的已记录内容生成单独近似结果，保留原文、诊断和不完整标记，
  用于观察统计；不再尝试补取完整 SQL，不进入正常基线训练或自动异常判断。
  这是对原失败输出范围的扩展，不把结构失败改为成功；近似接口已有独立实现，
  近似结果已由 #18 入库，观察统计仍未交付，见[近似接口说明](../../docs/design/sql-approximate.md)。
  后续已提供[可靠归一化入口](../../docs/design/sql-normalization.md)，继续保留失败状态与结果隔离。
- SQL 文本缺失或不完整，无法可靠生成结构指纹时，相关样本暂不进入基线；
  文本完整但解析器暂不支持其语法时，同样暂不训练，单独标明解析支持不足。
  解析器不支持并不证明 SQL 本身无效或曾执行失败，不能伪造 SQL 执行错误状态。
- 多语句批次只有部分能够可靠解析／归一化时，整批暂不训练；不摘取可解析的
  子语句并把整批 duration 当作其耗时，也不猜测各部分耗时。
- 能可靠界定影响范围时，记录诊断原因、数量及日志来源／文件位置，继续处理
  其他可靠记录；问题记录数不等于执行次数。无法归属 SQL 分组的问题沿用
  导入批次层面记录，不因已有 duration 就构造可靠结构分组；近似观察按上述独立
  契约保留来源、记录／事件单位和计时依据，不把日志出现次数当作执行次数。
- CSV 结构损坏、记录边界不可靠时仍按文件失败处理，阻止该集群本批次发布；
  记录级问题处理不能绕过批次完整性与后续质量检查。
- 此规则不保证最终指纹覆盖率。已有五类计时的日志位置覆盖率不是可靠指纹
  生成率或合格训练样本覆盖率，实际指纹覆盖需在实现后验证。
- 本次不选定解析器或指纹算法；需要保留的明细所对应可靠原文采用上述另行
  确认的精确去重保存方式；问题记录已按结构 1.2.0 由 #18 写入，各类留存期限仍待定。函数参数
  字典的具体规则及其回退仍由既有 Issue 单独确认，不把字典缺少条目
  自动等同于无法识别 SQL 结构。
