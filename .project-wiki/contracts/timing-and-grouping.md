# 计时分类、分组与时间归属

## Summary

五类计时分别统计；完整请求、阶段和调用的单位保持区分，开始时间标明推算性质。
实现日志计时识别、Execute 配对、分组或时间归属时阅读。

适用范围：以下为首期 HashData 契约；设计后续来源接入时，参照
[多类型系统接入约束](../decisions/project-scope.md#已确认的多类型系统接入扩展约束)。

## Contracts

### 已确认的基线分组维度

- 确认日期：2026-09-22。
- 来源：在“计算集群＋数据库＋SQL 结构指纹”的分组建议基础上，用户明确要求
  “执行的用户不同也进行拆分”。
- 来源状态：current；已确认基本分组维度，尚未实现聚合逻辑。
- SQL 身份的基本分组为 **计算集群＋数据库＋执行用户＋SQL 结构指纹**。
- 用户于 2026-09-24 在此基础上确认加入计时类别进行统计聚合，逻辑 GROUP BY
  为 **计算集群＋数据库＋执行用户＋SQL 结构指纹＋计时类别**，具体类别见下文。
- 指纹对应单条 SQL 或整个多语句批次，两类按上述已确认粒度分别统计。
- 相同 SQL 指纹在不同计算集群、数据库或执行用户下分别统计执行样本并建立基线。
  执行用户是分组维度，不仅是查询筛选条件。
- 指纹相同且其余三个身份维度均相同的记录属于同一 SQL 基本分组，聚合时还须
  按计时类别分别统计，不把不同类别的样本混合。完整执行样本仍按下述暂定
  门槛判断；阶段／调用沿用下述已确认的试行数值并独立检查，其他质量和异常判断规则继续落实。

集群通过导入时明确选择的日志来源及人工维护的映射确定，见上述已确认规则；
数据库和执行用户的具体字段映射、标识的配置存储与解析实现仍待落实。

关联条款：[首期 schema / search_path 处理边界](sql-fingerprints.md#首期-schema--search_path-处理边界)；[已确认的业务常量归一化](sql-fingerprints.md#已确认的业务常量归一化)。

### 已确认的五类计时统计与 Parse／Bind 纳入

- 确认日期：2026-09-24。
- 来源：在列明五项 GROUP BY 为集群、数据库、执行用户、SQL 结构指纹和
  计时类别后，用户明确提出“把parse和bind也加入进来吧，也可以直接契合
  这五项吧，样本可能较少，如果样本量不够，就只观测也可以”。
- 来源状态：current；已纳入首期需求，统计、指纹和配对功能尚未实现。
- Parse 和 Bind 是第五项 `timing_type` 的两个新增取值，不新增第六、第七
  个基础分组字段。逻辑字段名仅为示意，不在本次固定物理表结构。

| 计时类别 | 当前已核查构建的日志位置／识别依据 | 样本单位 |
| --- | --- | --- |
| 请求整体 | `postgres.c:1946` | 满足资格的单条／整批请求 |
| Execute 首次 | `:2843`，与 `:2764` 的 execute 消息可靠配对 | 一次首次调用 |
| Execute 续取 | `:2843`，与 `:2764` 的 execute fetch from 消息可靠配对 | 一次续取调用 |
| Parse | 合并 `postgres.c:2219` 与 `:2224` | 一次可可靠识别、归属的 Parse 阶段调用 |
| Bind | 合并 `postgres.c:2603` 与 `:2608` | 一次可可靠识别、归属的 Bind 阶段调用 |

- Parse／Bind 各自合并简略、详细输出分支的样本集合，不能只采用带显式阶段
  标签的慢日志；“合并”不表示相加不同阶段的耗时。源码行号仅用于识别类别，
  不直接作为聚合维度；会话、进程、portal 和命令号用于关联，不是这五项
  GROUP BY 的附加字段。来源映射只覆盖已核查构建，不能不分版本硬编码。
- 沿用[已确认的时间统计粒度](baseline-statistics.md#已确认的时间统计粒度)：
  整体按上述五项分组，其他层次分别按对应的推算开始时间分桶，使用北京时间。
  阶段／调用的推算开始时间是本次阶段／调用结束时间减其 duration，不声称是
  整条 SQL 的开始时间。每类、每个时间范围使用自己的样本计算适用的主要统计指标。
- 样本不足时保留可计算指标、样本量、实际覆盖及不足提示，**仅作观察，不用于
  自动异常判断**。样本条件按每个五项分组及相应时间范围独立解释，不能从
  同一 SQL 的其他阶段借用样本。Parse／Bind 的调用样本量不能与完整执行
  次数互换；用户已确认下述阶段／调用试行门槛。达标只表示满足数量条件，
  不据此直接判断整条 SQL 的 activity 异常，也不自动确认阶段级异常判断方法。
- 阶段样本的 SQL 身份、计时含义和 duration 必须可靠。若无法可靠归属 SQL
  分组，按导入批次记录问题，不为缺失或不可靠文本构造虚假的 SQL 分组。
- 类型未知仍是识别状态，不是新增的第六类已确认耗时基线。完整 SQL 执行
  次数、排除执行总数和训练资格继续按原执行单位解释，不能将 Parse、Bind
  或续取日志加总为业务执行次数。
- 独立保留 Parse／Bind 分布不要求把其耗时累加到 Execute 或请求整体，也不
  要求还原全阶段链。`1455` 仍待核实，autostats 组件计时不作为业务 SQL
  执行样本。统计公式、阶段／调用数量门槛及五类统一版本采用下述已确认口径；
  其他质量条件仍待落实。

关联条款：[已确认的时间统计粒度](baseline-statistics.md#已确认的时间统计粒度)；[已确认的阶段与调用样本门槛](baseline-statistics.md#已确认的阶段与调用样本门槛)；[已确认的主要统计公式](baseline-statistics.md#已确认的主要统计公式)；[已确认的五类计时统一版本与发布边界](../features/baseline-versions.md#已确认的五类计时统一版本与发布边界)。

  未覆盖来源、9 条未候选配对 Execute 和训练资格边界后，用户表示“这个覆盖率
  我觉得可以了”。
- 来源状态：current；这是首期范围的确认，尚未实施分类器或基线统计。
- 首期按上述五类计时推进。当前 46 文件的观察覆盖率为 119 的 99.02%、
  120 的 96.99%、合计 97.99%；扣除 9 条未候选配对 Execute 后，合计保留
  两位小数仍为 97.99%。详见[覆盖率证据](../../docs/reports/hashdata-duration-source-mapping-2026-09-24.md#已确认五类计时的日志覆盖率)。
- `postgres.c:1455` 和 `autostats.c:334` 暂不扩展为首期计时类别，后续再评估；

  五类。无法可靠配对的 Execute 继续标为类型未知。

  不代表配对准确率、有效训练样本覆盖率或基线质量已经验证。SQL 归属、样本
  资格、各类统计指标与质量规则继续分别落实。

### 已确认的 Execute 单次配对与调用分类统计

- 确认日期：2026-09-24。
- 来源：在明确“关联 2764，但首期只做单次调用配对；2843 提供 SQL、duration
  和结束时间，2764 判断首次或续取；可靠配对后分别统计，无法可靠配对标为
  类型未知；不要求还原首次到全部续取的完整执行链”的建议后，用户回复
  “确认这种处理方式”，并要求梳理当前统计分类维度。
- 来源状态：current；这是已确认的处理范围，配对器和统计功能尚未实现。
  日志证据及已知限制见[专项核查报告](../../docs/reports/hashdata-duration-source-mapping-2026-09-24.md)。
- 针对已核查的构建，使用 `postgres.c:2843` 的独立 SQL 字段、duration 和
  日志时间戳作为调用数据；通过同一次调用的 `postgres.c:2764` 消息获得
  `execute` 或 `execute fetch from` 分类及必要上下文。message 字段只有
  duration 不表示整条 CSV 没有 SQL。
- 在计算集群、数据库、执行用户及 SQL 结构指纹的基本分组内，**首次 Execute
  调用**与**续取 Execute 调用**分别统计。一次可靠配对形成一个调用样本，
  不把两条日志计为两个样本，也不把续取次数计为完整业务 SQL 执行次数。
- 无法可靠配对的标为**类型未知**，不强行归入首次或续取；该标记表示识别
  状态，不自动形成可用于完整 SQL 异常判断的第三类执行基线。无法可靠归属
  SQL 分组的问题继续留在导入批次层面。
- 配对需结合日志来源、可靠会话身份、顺序及文本／上下文校验；本次没有把
  SQL 指纹、最近时间或命令号相等单独确认为唯一执行键。算法、歧义处理的
  具体实现与验收样例仍待落实。
- 此分类是调用级诊断口径，与请求整体／完整执行基线分别解释，不将首次和
  续取混成同一个耗时分布，不与 1946 的请求整体耗时混合。仅有首次调用不
  证明 SQL 已完整结束，单次配对成功也不证明整个 portal 完成。
- 首期不要求为这些调用统计还原完整 portal 生命周期；没有确认将各段相加
  作为完整 SQL 耗时，也没有确认把调用统计直接用于整条 SQL 的 activity
  自动异常判断。原完整执行训练资格和样本门槛不能用续取调用数替代。
- 业务基线采用[已确认的时间统计层次](baseline-statistics.md#已确认的时间统计粒度)
  及全部主要指标，单条 SQL 与整批请求分别统计。调用分类不改变这些定义，统计公式采用
  下述已确认口径；调用数量门槛和五类统一版本见下文，其他质量条件仍待落实。
  调用推算开始时间对应本次调用，不等于首次 SQL 请求的开始时间。
- 此项配对确认只针对 Execute；用户随后已确认上节的 Parse／Bind 独立阶段
  统计。1455 的计时含义仍待核实，autostats 组件计时不作为业务 SQL 执行基线。

### 已确认的时间口径

- 确认日期：2026-09-22（业务时区）；2026-09-23（统一修订为推算开始时间归属）。
- 来源：用户此前确认统一按结束时间归属；在讨论后续 activity 比对、跨小时
  执行及启动时间偏移后，对训练窗口、活跃天数、按天统计和小时画像全部改为
  按推算开始时间归属的整体修订建议回复“确认”。本次确认替代此前的结束时间
  归属规则，原有决定作为历史记录保留在[变更日志](../log.md)。
- 来源状态：current；已确认业务时间口径，尚未实现时间解析、转换或日期归属。
- 首期统一使用 **北京时间（UTC+8）** 划分自然日、展示时间，以及解释手工
  填写的故障或维护时段。
- 日志按其来源时区解析后转换到统一业务时区。本次确认不代表已经核实现网
  各日志来源的原始时区配置；具体来源时区配置及解析方式留待落实。
- 对 2026-09-23 提供的单一 Master 生产样本，用户明确确认 CST 为北京时间，
  本次按 UTC+8 解释；这是用户提供的来源信息，不是已读取源端配置的验证结果，
  不自动推广到其他日志来源。
- 已完成 SQL 按 **推算开始时间** 对应的北京时间日期，归入训练窗口、活跃
  天数及按天统计；按小时画像使用推算开始时间对应的北京时间小时。一次跨天
  或跨小时执行保留完整执行耗时，不拆成多个日期或小时的执行样本。
  2026-09-25 新增逐周与跨周星期同样按推算开始时间归属，跨周也不拆样本；
  自然周边界及不足整周的处理见[时间统计粒度](baseline-statistics.md#已确认的时间统计粒度)。
- 例如北京时间 7 月 23 日 00:10 结束、耗时 20 分钟的 SQL，推算开始时间为
  7 月 22 日 23:50，归入 **7 月 22 日、23 点时段**，保留完整 20 分钟耗时。
- 开始时间决定统计归属；执行完成并导入、且满足既定训练资格后才能纳入基线。
  如果完成日志次日或更晚才导入，在后续新版本构建中纳入，前提是推算开始日期
  仍在该次训练窗口内。运行中的耗时不作为完整训练样本。
- 推算开始时间同时用于执行区间展示和故障或维护时段排除。排除仍按整个推算
  执行区间与排除时段是否重叠判断，统计日期及小时归属不改变该规则。
- 小时画像描述在各小时开始的已完成执行的完整耗时分布。activity 的比较
  参照按下述已确认规则选择开始小时画像，不足时回退同组整体基线；使用各自
  已确认的样本条件，其他质量条件及邻近时段参考继续待定。排除时段的端点及
  零耗时匹配按上述已确认规则执行，完成记录的具体识别方式仍待落实。

关联条款：[已确认的训练窗口](baseline-statistics.md#已确认的训练窗口)；[已确认的 activity 基线参照选择](../features/sql-search-and-views.md#已确认的-activity-基线参照选择)。

### 已确认的首期执行时间估算假设

- 确认日期：2026-09-22。
- 来源：用户明确提出“首期可以假设parse和bind可以忽略，用结束时间和duration
  推算一个开始时间”。
- 来源状态：current；这是用户接受的首期简化假设，不是已经通过生产日志或
  实际 activity 对照验证的计时精度结论，功能尚未实现。
- 对完整 SQL 执行区间的首期估算，继续采用忽略 Parse、Bind 贡献的简化假设，
  不要求重建并累加各阶段来拼接总耗时。独立 Parse／Bind 统计已按前文纳入。
  对选定的 SQL 完成记录，使用其日志时间作为结束时间，使用其 `duration`
  作为首期执行耗时；按日志单位换算后计算：
  **推算开始时间 = 结束时间 − duration**。
- 开始时间标明为推算值，与日志提供的时间区分，不声称与实际开始事件或
  `pg_stat_activity.query_start` 精确相等。
- 不要求为了取得开始时间而查找、配对另一条开始日志，也不将精确还原协议
  各阶段作为该估算方法的前提。执行跨小时、跨日时保留完整 `duration`，
  故障或维护时段排除使用推算开始时间至结束时间的区间。
- 完成记录的识别及已确认的训练资格继续适用：这项假设不把明确的 Parse、Bind
  阶段记录另算成 SQL 执行，也不将失败、取消、超时或信息不可靠的记录自动纳入。
  具体解析及记录归属规则留待落实。
- 后续取得的生产样本出现分钟级 Parse/Bind 耗时，见上述生产观察。其开销并非
  总可视为很小，需要继续评估总耗时估算假设的适用范围。用户现已确认独立
  统计阶段分布，但尚未确认累加阶段作为完整 SQL 耗时，也未验证与 activity
  开始时间精确对齐。
