# 生产 SQL 日志样本分析

分析日期：2026-09-23。用户提供单一 Master 的生产日志，并确认源日志中的 CST
表示北京时间（UTC+8）。核对文件末端后，用户进一步确认：9 月 20 日后续日志
未包含在本次拷贝中。因此本次范围为 **9 月 19 日全天，以及 9 月 20 日截至
09:37:54 的已提供文件**，不能作为两个完整自然日计算日均量或验证完整日批次。

本次是需求阶段的本地只读调查，不是导入器、指纹算法或基线构建的实现验收。
报告仅保留统计、校验值和复查位置，不包含业务 SQL、参数值、账号、库名或地址。
原始日志仍由 Git 忽略，未修改、提交或上传。

## 主要结论

- 已提供的 7 个文件共 2,825,293,129 字节，约 2.63 GiB；有 2,499,534 条
  CSV 逻辑记录，全部具有 30 列结构。多行字段使其对应 38,296,215 个物理行，
  不能按文本行数统计执行，也不能按换行拆分 CSV。
- 生产日志不能直接沿用“每条耗时日志均带完整 SQL”的测试样本观察。
  耗时记录中有 SQL 字段为空、文本截断迹象和 UTF-8 不完整的情况。
- 发现明确的 Parse、Bind 耗时记录，分别达到约 2 分 46 秒和 9 分 48 秒。
  “忽略 Parse/Bind”仍是此前已确认的简化假设，但生产证据表明它们并非总可
  视作很小的开销；需要重新评估其适用范围，本次不自动修改需求。
- SQL 字段中存在多个语句组成的文本。不能把文本的第一个关键字直接作为整条
  耗时记录的黑名单判断依据，也不能把同一个 duration 分配给每个子语句。
- 文件 gzip 压缩与 SQL 原文精确去重都有实际收益，但这不是 PostgreSQL
  数据库容量测量，留存期限、原文存储方式和执行明细模型仍未确认。

分位数使用排序后线性插值计算，仅描述本次所有耗时日志的混合分布，含协议阶段、
维护及黑名单等记录，不能作为某条 SQL 的基线或异常阈值。

明确标有 `duration: ... ms parse ...` 的记录 3 条，耗时 76,124.336～166,208.955 ms；
明确标有 `duration: ... ms bind ...` 的记录 22 条，耗时 61,896.220～587,916.647 ms。

另有 15,000 条耗时来自 `autostats.c:334`，需要与业务语句完成耗时区分。

[PostgreSQL 9.4 日志说明](https://www.postgresql.org/docs/9.4/runtime-config-logging.html)
说明扩展协议各阶段可分别记录耗时；以上显式阶段数量和时长来自本次生产文件。

Warehouse 3.13.13，并提供 `log_duration = on`、`log_min_duration_statement = 1min`、
`log_statement = all`、`log_min_error_statement = error`，已记录到

也不单独构成业务执行成功的完整证据，仍需满足已确认的训练资格。

- `SET → SELECT`

## 对后续需求的影响

1. 导入文件枚举必须覆盖此次实际存在的轮转后缀；时间范围应从日志内容读取。
   本次 9 月 20 日样本不是已完成的全天批次，不能仅因全部已提供文件读完就
   认定该日批次完整并发布新基线。
2. 首先落实完成记录识别、内部或协议阶段区分、多语句文本的执行归属。现有
   成功完成、耗时完整、关联可靠的训练资格继续适用，不能仅凭有 duration 入选。
3. 编码及文本完整性异常可以定位到记录，适合依据既有规则记录原因、隔离受
   影响执行；不要静默丢字节、补齐 SQL 或生成看似可靠的指纹。具体恢复方式待定。
4. 重新讨论忽略 Parse/Bind 的适用范围及将来与 activity 计时的对齐；已确认的
   “按推算开始时间归属”不因本次调查自动改变，估计精度尚未与 activity 实测对照。
5. SQL 原文精确去重和原日志压缩值得纳入后续存储方案讨论；需要更多完整日期
   和业务周期数据评估留存与稳定性，本次不固定存储期限或训练阈值。
