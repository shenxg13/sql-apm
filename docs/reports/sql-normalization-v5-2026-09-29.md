## 实现与验证方法

- 当前算法 `sql-normalization/5`，解析能力 `mpp-adapter/9`、pglast 7.18、字典 1.0.1 不变。
  SELECT 目标列表和 JOIN ON 使用 WHERE 业务值与四档 IN 规则；
  集合运算分支按独立 SELECT 恢复 WHERE、函数及 FILTER 规则。保护边界见[指纹契约](../../.project-wiki/contracts/sql-fingerprints.md)。
- 冻结 v4 提交为 `9a0f9f507a4e068f32c8704da28c761d6e65ca14`；
  v5 实现提交为 `ce1bcb8d418c8e47f4e5fc6a441365bfb5a5159f`。
  仅向冻结 checkout 复制两份诊断模块，未改其产品核心。v4／v5 指纹不能直接比较，
  以下按成员集合和完整结构摘要核对。
- 独立投影不调用 v5 walker：两类新位置由明确字段／保护规则投影；
  集合分支包装为独立 SelectStmt，调用经版本检查的冻结 v4 walker，再投影新位置。
  171 条人工 SQL 保存实际冻结结构及仅恢复集合分支后的结构；不依赖真实样本碰巧覆盖边界。
- 全量分类采用“仅 SELECT → SELECT＋JOIN → 集合分支恢复”顺序：
  每个最终合并组归入最早足以形成该组的步骤，混合原因归入最后所需步骤。
  三类互斥、和为全部合并组；不把它解释成三个独立反事实实验。

## 与需求阶段的对照和限制

需求阶段 v4 基础覆盖为 119 的 90.0%、120 的 56.6%，本次分别为 90.01%／56.61%，
按一位小数完全复现。正式 v5 为 90.99%／60.02%，较冻结 v4 增加 0.99／3.41 个百分点。
需求阶段 SELECT 单独方案为 90.7%／59.8%，JOIN 单独方案为 90.0%／56.7%；
当时候选未增加新位置 IN 分桶，也没有恢复集合分支。本次还采用最终组的互斥顺序归因，
含多个原因的组只归入最后所需步骤，不能将分类表当作独立候选的直接复测。

原文→v4 参照可比样本 207,090／371,201，以及 SELECT 的 5,518／84,422，
均与需求阶段完全相同；119 JOIN 的 180 也相同。120 JOIN 从 551 增至 1,047，
本次该类别包含新位置 IN 及 SELECT＋JOIN 共同形成的最终组，比较集合与原独立 JOIN 方案不同。
集合分支新增 17,847／1,125 个可比样本，需求阶段没有进入这些分支，不能视为原诊断的遗漏值补齐后仍保持原结论。

另外，在仍留存的需求阶段 `dispersion_eval.py` 中发现实际倍数是
`(max_median_ms + 1) / (min_median_ms + 1)`，与正文概称的“中位数最大／最小倍数”不同。
正式命令使用不加偏移的直接倍数及上述零值规则；这解释了样本数一致而部分分桶不同。
用最终只读缓存及相同分组重新运行 `summarize`、仅将 `ratio_bucket(min,max)` 的输入改成
`min+1,max+1`，所得两集群原文→v4、SELECT 和 119 JOIN 的四档占比均在一位小数上
复现在线 Issue 的历史数值。例如 119 SELECT 的 ≤2 倍由直接公式的 84.56% 变为 91.8%，
119 参照的 >10 倍由 10.27% 变为 9.4%；120 参照四档变为 36.9%／17.7%／30.3%／15.1%。
[公式敏感性核对](data/sql-normalization-v5-historical-ratio-2026-09-29.json)记录输入摘要、旧脚本摘要及结果，
仅用于解释历史口径，不替代正式命令的验收结果，也未改写旧报告或在线历史证据。

全部新增合并的 >10 倍样本占比为 119 的 3.50%、120 的 0.97%。
但集合分支恢复单独为 4.62%／19.73%；120 只有 18 个可比组、1,125 个可比样本，
其中 3 组的 222 个样本落在 >10 倍，高于该集群 v4 参照的 15.22%。
该有限集合的离散风险须保留，不能用全部合并的较低占比掩盖；契约未设离散度数值放行门槛。
两个集群取自不同月份，120 只有七天；自然日期、系统负载和 SQL 参数都可能影响耗时。
这些观察不证明所有新合并都等价，也不保证生产稳定性或执行计划相近。
