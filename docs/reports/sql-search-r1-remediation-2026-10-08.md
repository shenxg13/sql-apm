## 函数内部实际计划

在新副本的诊断管理员会话加载 PG17 自带 `auto_explain`，开启 `log_nested_statements`、
`log_analyze`，关闭逐节点计时；外层强制通用计划，以验证函数局部配置能覆盖它。
独立计时使用普通项目角色且不启用计划日志。命令行另用诊断会话预加载同一模块，
从实际 PostgreSQL 日志捕获完整批次的逐条提示；不是用表面 `EXPLAIN SELECT 函数()` 代替内部计划。

只有一条记录的结构，`mpp_query_exact`、指纹值 `mpp_query_search`、带身份的命中列表，以及
整批未命中的 CLI 第一条提示都得到如下实际计划：

| 表 | 扫描方式 | 实际使用行数 |
| --- | --- | ---: |
| mpp_fingerprint | `mpp_fingerprint_value_idx` 的 Index Scan | 1 |
| mpp_occurrence | `mpp_occurrence_sql_time_idx` 的 Bitmap Index Scan + Bitmap Heap Scan | 1 |
| mpp_baseline_group | 现有 scope/profile/normalization/database/user/fingerprint/timing 唯一索引的 Index Scan | 1 |

未命中的整体及另一条提示在指纹索引返回 0 行后停止；不会顺序扫描这三张全表。
会话的 `plan_cache_mode` 在调用后恢复，合成验收在外层强制通用计划下连续七次核对结果及配置不变。

## 性能复测（measured）

开发机、PG17.10、Python3.9.5，数据为 55 文件、1,385,776 份原文、7,424,804 条记录，
930,187 个正式分组。`shared_buffers=512MB`、`work_mem=16MB`，与原测量一致。
下面四类结构与 R1 使用同一选择规则；一条记录、记录最多及身份最多使用 R1 的同一固定样本。
每项三次连续计时，已完成其他回归后串行执行；选样已读过部分数据，不称为冷盘。

| 结构 | 记录数／身份数／原文数 | R1 数据库精确毫秒 | 整改后精确毫秒 | 整改后指纹直查毫秒 |
| --- | ---: | ---: | ---: | ---: |
| 一条记录 | 1 / 1 / 1 | 1,025–1,083 | 2.399–5.836 | 2.432–2.553 |
| 记录最多 | 392,887 / 25 / 1 | 1,838–2,259 | 444.102–509.533 | 461.509–464.216 |
| 身份最多 | 263,930 / 54 / 454 | 1,879–3,519 | 441.273–455.985 | 451.027–453.201 |
| 原文最多 | 374,838 / 1 / 62,473 | 1,766–1,907 | 439.040–450.972 | 428.166–456.344 |

| 完整 CLI 输入（含进程、归一化、连接和 JSON） | R1 秒 | 整改后两次秒 |
| --- | ---: | ---: |
| 一条已有语句 | 1.18–1.23 | 0.183295 / 0.185580 |
| 五条各自已有、整体未出现 | 5.41–5.45 | 0.197216 / 0.173566 |
| 二十条各自已有、整体未出现 | 21.05–21.10 | 0.217218 / 0.210634 |

批次采用 R1 同一固定哈希选出的 20 条语句，确认整体 `not_seen`，20 条提示均有记录。
R1 原来的固定约一秒成本来自每次扫描全库记录、指纹，以及每身份扫描分组；原报告只归到
同结构原文／记录，解释不完整。这次改写去掉了这项与全库量直接相连的固定成本。

规模解释（推断）：现在精确聚合主要随匹配原文、其执行记录及身份数增长；索引大小、缓存、
规划器估算仍会影响实际耗时。密集结构允许规划器选择顺序扫描，不宣称所有输入都只能走索引。
逐条提示最多另做20次查找，成本是各条累加，遇到20条密集结构不能套用本表的稀疏样本耗时。
模糊检索仍扫描全部原文并聚合匹配记录；本轮没有声称消除宽泛文本输入的线性全库成本。
本地一个集群只有7天、生产首批30天且原文／执行记录累积，不能据此推定生产时延。

## 同类计划检查与建议 5

| 路径 | 实测及处理理由 |
| --- | --- |
| `mpp_query_statistics` | 已补 profile，稀疏结构的正式分组以完整唯一索引查询；不再按集群前缀遍历全部组 |
| 明细、时间汇总、默认时间边界 | 调用函数局部定制计划；稀疏结构的指纹及记录均索引读取。内部 `mpp_query_occurrences` 仍内联 |
| 显式时间边界 | 已给结束时间时直接计算，实际嵌套计划不读取任何表；起止都给时不再求该身份最新记录 |
| 历史的缺失规则计数 | 保留，实测 678.526–690.196ms。契约要求当前事务中全库未按当前规则生成结果的准确份数；不引入缓存或新表及相应写入维护，避免过期警告。这项成本仍随全部原文和指纹增长 |
| 模糊检索的可空身份／时间参数 | 使用局部定制计划；仍须扫描原文／当前规则指纹以做任意片段匹配。无匹配的本次稀疏筛选实测记录扫描只取1行便终止；不把它误称为索引能消除原文扫描 |
| 版本列表／版本选择 | 通用计划只涉及13个构建及相关元信息，没有进入执行记录或指纹大表；保留 SQL 内联与后续筛选能力 |
| 观察统计的可空身份条件 | 实测顺序扫描1,074个观察组（使用1行、过滤1,073行）。当前近似值条件缺少可用的现有前导索引；本轮保留，增长随观察组数，读取统计仍用既有结果函数和锁，不扩大正式基线含义 |
| 基础 occurrences 的外部 prepared statement | 特意强制通用计划时仍可能扫描全部执行记录，本次7,424,804行中过滤7,005,439行。改为外层定制计划后稀疏结构走指纹／记录索引。保留其可内联属性以便外层 LIMIT、筛选和聚合下推；函数级配置会阻止内联。产品历史／汇总调用处已处理；外部长期可空参数 prepared 调用须采用定制计划，开发说明已给出事务设置 |

  1.9回执保留，1.10回执等于本轮schema文件SHA-256。原文表含索引从1,055,227,904到1,605,083,136字节，

  发布33项，清理23项，检索8组（含本轮新增断言）均通过。制包边界30项、完整离线Harness通过；在线检查绑定最终交接评论。

## 复现与证据边界

- 本地私有副本和日志：`var/issue47-r1-fix/`；升级由关闭的 #45 1.9 原件复制，升级脚本83.549秒。
- `verify_search_full.py prepare/audit/exact`：全量旧列摘要、独立匹配与基础表对照及首次／重复计时。
- `verify_search_plans.py --directory var/issue47-r1-fix/full`：嵌套实际计划、四类结构、完整批次与长输入。
- R1 的三个 oracle 保持原文件不变，由私有包装器只改连接到本次副本；这是实施方复跑他方脚本，
  不替代 R2 评审者在新 head 的独立执行。两个数据 oracle 沿用其会话 `work_mem=256MB`；
  它们附带的耗时仅为核对运行记录，不混入本报告 `work_mem=16MB` 的性能表。
  原始SQL和身份、带参数计划留本地，公开机器记录只保留数量、摘要和节点名。
- 最终提交、相邻整改差异和在线检查由 PR 的整改交接评论绑定。目标分支／merge base 保持原固定值，
  `initial_head_sha=423e047ee963ae113f4114caafd41a93621807e5` 不重置。
- 用户先前筛选及业务常量补验的30份用例证据仍保留；维护者明确要求的 S23 最终确认与独立 R2 尚需完成，
  本报告不作为合并批准。本次不发版、不做 Kylin 或 Grafana 部署。
