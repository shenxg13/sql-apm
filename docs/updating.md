# 人工更新流程

## 下游采用模板更新

1. 记录已采用的模板提交或发布版本，以及项目本地定制。
2. 阅读新版本的 Git diff、[Harness 更新日志目录](../.harness/update-log/)（按文件名排序）、
   接口和工具版本变化；[旧更新日志](../.harness/update-log.md) 保留冻结历史。
3. 区分通用文件与项目所有的 README、运行模型、知识和业务检查。
   `scripts/quality/project_checks.sh` 归项目所有，采用更新时保留项目自己的版本。
4. 在独立任务分支选择需要的修改，审阅冲突，按项目流程确认行为变化。
5. 执行通用质量检查与受影响的项目检查；重大变化进入独立评审。
6. 更新采用版本和本地定制记录，保留来源与验证证据。

`.harness/sync-status.json` 的 lastSyncedCommit 可由采用项目记录已审阅版本；
留空代表尚未记录，不代表自动跟踪上游。首版没有自动同步、生成器或覆盖操作。
项目运行模型、历史验收、业务知识与本地配置由各项目维护。

## 下游改进回流模板

下游项目改动了通用流程、脚本或模板后，可以把其中通用的部分取回本仓库。

1. 以下游记录的采用版本为基线，比较通用文件，确认模板在此之后是否也有变化。
2. 把差异分成三类：可原样取回的、需要去掉项目内容后改写的、属于项目自己不取回的。
   业务检查命令、项目知识、项目范围和运行模型不取回。
3. 在本仓库的独立分支上修改，内容取自下游已合并的主分支，不取未合并的工作区。
4. 改写时去掉项目名、仓库地址、Issue 链接、本机路径和业务主题；来源仓库、提交和取舍
   只记在[来源记录](provenance.md)，其他文件不出现这些标识；把新来源的项目名等字面标识
   加入该页的 `source_markers` 审计配置，扫描只识别已登记的标识。
5. 运行 `scripts/quality/check.sh`；它包含的模板回归会用来源标识扫描除来源记录以外的全部文件。
6. 在 `.harness/update-log/` 新建独立条目，说明行为变化和下游采用时要注意的事项；
   知识摘要写入 `.project-wiki/log/`，链接到所属主题。两处均一次变更一个文件，文件名为
   `YYYY-MM-DD-标识.md`；标识只用小写字母、数字和连字符，有 Issue 时以 `issue-N-`
   开头并接简述。两份原日志保留已有条目，不迁移、不改写、不再追加。
7. 模板合并后，下游把记录的采用版本更新到新提交，并核对本地定制记录。

下游在自己的 Harness 更新日志目录里为每次流程改动建立独立条目，并注明是否来自上游，
回流时就能找到要比较的提交。采用日志分文件规则时保留两份原日志的全部历史，只在开头
说明新位置；同步工作流、知识维护方法、检查单和文件名检查，新条目使用目录。
