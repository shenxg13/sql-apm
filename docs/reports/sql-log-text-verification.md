# SQL 日志文本与绑定参数核查

核查日期：2026-09-23。范围为用户提供的两份测试环境 CSV；本次为只读样本调查，
不是业务解析器的实现验收。未读取生产日志、源端日志配置或客户端原始请求。

结论：测试样本中的耗时记录均携带 SQL 文本，未发现明显截断迹象；部分文本保留
参数占位符，其参数值在 `execute` 记录的 `DETAIL` 中，耗时记录自身未携带这些
参数值。因此，完成记录中的 SQL 文本不能一概理解为已代入实际参数的语句。

后续补充：本报告仅对应此前两份测试文件。2026-09-23 新提供的生产样本分析见
[生产日志报告](production-log-analysis-2026-09-23.md)；以下“未取得生产日志”等
表述描述本次测试核查当时的证据边界，不能代替后续生产观察。

## 输入与方法

| 文件（位于 `raw/inbox/hashdata/`） | 字节数 | SHA-256 |
| --- | --- | --- |
| `gpdb-2026-07-22_000000.csv` | 77,857,012 | `a3f60da951297a8411f7737f955bb730a674369997bcbc924366e2bcfe5861b3` |
| `gpdb-2026-07-23_000000.csv` | 97,315,071 | `e5811fa4015c65783ab10adfa771ba10bef946cc36f52f5c56622085249da8af` |

使用现有 Python 3.9.25 的标准库进行临时诊断；未安装依赖或创建项目运行环境。
项目 Python 3.9.5 的约定不变。检查过程未修改输入，检查前后文件大小、修改时间
一致，SHA-256 与此前保留的输入标识一致。输出仅包含汇总及记录定位，无 SQL
原文、参数值、账号或地址。

- 全量按严格 UTF-8、CSV 逻辑记录读取并核对 30 列结构，支持字段内换行。
- 对消息以 `duration: ... ms` 开头的记录，检查第 25 列 SQL 文本。
- 检查引号、括号、嵌套注释和美元引用的闭合情况，区分注释、字符串与真正的
  `$n` 占位符；因源端字符串配置未知，分别考虑普通字符串的两种反斜杠模式。
  这是词法检查，不是完整 SQL 语法解析。
- 检查显式截断标记、尾部省略号、NUL、Unicode 替换字符，以及常见固定长度
  边界；对照同条 `statement`／`execute` 消息中的 SQL 文本副本。
- 对 `execute` 的 `parameters:` 明细检查参数赋值列表及引号闭合，核对其编号
  是否覆盖 SQL 中引用的占位符。未将参数替换进 SQL，也未执行任何业务 SQL。

SQL 文本方面：

- 最长 SQL 文本为 19,681 个字符，在该样本中也是 19,681 个 UTF-8 字节。
- 未发现两种字符串模式下均存在的词法闭合问题；也未发现显式截断标记、尾部
  省略号、NUL 或 Unicode 替换字符。源端两种字符串模式未改变本样本检查结果。
- 118,587 条 `statement`／`execute` 消息的 SQL 部分，均与同条 CSV 第 25 列
  在去掉首尾空白后完全一致，未发现 SQL 字段短于该消息副本的情况。
- 所有耗时记录的 SQL 文本，均能在这两份文件的 `statement`／`execute` 消息中
  找到相同文本。这是文本集合比较，不证明已逐次关联每一次执行。
- 未在 1,023／1,024、2,047／2,048、4,095／4,096、8,191／8,192、
  16,383／16,384 等常见长度边界观察到文本，未见这些边界上的截断迹象。

参数方面：

- 294 条含占位符的耗时记录，其 `DETAIL` 均为空，单靠该行无法取得实际绑定值。
- 98 条带占位符的 `execute` 记录在 `DETAIL` 中提供参数值或 `NULL` 表示；
  每条均覆盖其 SQL 引用的全部参数编号，参数列表及字符串引号闭合。
- 参数数量分布为：58 条含 1 个、17 条含 2 个、22 条含 5 个、1 条含 183 个。
- 294 条含占位符的耗时记录，均能在相同会话、相同 SQL 文本范围内找到带参数的
  `execute` 记录。这只是关联线索，尚未验证适用于重复执行等情形的唯一配对规则。

## 有界复查位置

使用 CSV 解析器按逻辑记录从 1 计数；物理行号仅用于编辑器定位。

下列两条均在 `gpdb-2026-07-22_000000.csv` 中：

| 逻辑记录 | 物理行 | 消息类型 | 日志时间（保留源时区标记） | SQL／参数情况 |
| --- | --- | --- | --- | --- |
| 184724 | 262214 | `execute` | `2026-07-22 15:50:47.877917 CST` | SQL 长 194 字符，含 `$1`～`$5`；`DETAIL` 中五个参数编号均有赋值 |
| 184759 | 262252 | `duration: 17129.034 ms` | `2026-07-22 15:51:05.006979 CST` | SQL 文本相同；`DETAIL` 为空 |

两条记录的进程、会话开始时间、会话编号及命令编号均相同，SQL 文本逐字符一致。
中间有其他会话日志，不能将物理相邻行作为配对条件。这里仅确认这个有界实例的
字段关系，不把它推广为完整的执行关联算法。

最长 SQL 位于同一文件逻辑记录 194749、物理行 289927～290115；SQL 字段长
19,681 字符，词法闭合检查通过。

## 结论的边界与首期含义

“未发现明显截断”是当前证据支持的结论。没有客户端原始 SQL 时，词法闭合及日志
副本一致不能证明不存在一切截断；参数编号齐全也不能独立证明值与客户端输入
逐字节相同。生产日志与源端配置尚未取得，不能将测试结果推广为生产保证。

对于 SQL 结构指纹与耗时统计，保留占位符的 SQL 文本可以作为后续解析输入；
如果要还原某次执行的实际参数，就需要读取并正确关联相应的 `execute` 参数明细。
本次不新增参数还原功能或参数留存要求，也不改变用户已接受的首期时间估算假设。

背景参考：[PG 9.4 日志说明](https://www.postgresql.org/docs/9.4/runtime-config-logging.html)
说明了扩展协议下 `log_statement` 与 Bind 参数记录的关系。以上数值与字段结论
来自本地样本，不根据该文档推断 HashData 现网配置。
