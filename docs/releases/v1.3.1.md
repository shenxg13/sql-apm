## 相对 v1.3.0 的变化

- #82 修复带历史导入时对窄记录的全表扫描；结构迁移只替换两个维护函数，不改表、索引和业务数据。
- 升级入口核对正式 v1.3.0 清单，按函数替换估算空间；事务失败自动回滚，成功后替换程序并恢复原服务状态。
  配置、密码文件、sqlfind 配置、每日运行单元继续可用。
- 复用固定 Kylin 运行时：Python 3.13.16 与 PostgreSQL 17.10；归档 SHA-256
  `d271d6a1471c41723724b48afad59f9675e1b324747fbb7dfae283f97340314c`。
  Python 依赖、RPM、Grafana 和插件不变，不重新编译。
- 独立检查工具包 1.3.0 只接受 v1.3.1／1.15.0；附只读导入采集 SQL 和定向补测步骤。
  v1.3.0 继续使用工具包 1.2.0，性能结果包格式和脱敏规则不变。

## 更正

2026-11-11：#73 的“导入 +18.3%”只是空库四文件的开发测量，不能用于预测生产带历史导入。
生产 v1.3.0 上，两个受影响集群每条记录的逐文件提交前耗时约为 v1.2.0 的 **4–6 倍**（观察），
另一个对照集群基本不变；该口径不包含文件事务提交时的延迟维护。
v1.3.1 开发机带历史配对相对 v1.2.0 为 **+19.59%**（measured），生产规模模型为
**+19.6%～+21.6%**（modeled）。这些结果不能替代生产实测，且单次配对的系统缓存不统一。
详见 [#82 报告](../reports/query-refresh-2026-11-11.md)。

## 已验证

继承 #82 的开发机带历史结果：迁移 0.624 秒；迁移前后业务内容及物理行位置不变；
三个时机的独立一致性检查均为 0。发布实现核对迁移文件及结构脚本与 #82 合并提交相同后继承证据。
本版验证机已完成正式 v1.3.0 身份对齐、迁移失败自动回滚和正常升级；迁移命令实测 0.665 秒，
业务内容与配置保持一致，17 项随包自检及检索、看板、sqlfind 核对通过。
升级后一次每日导入加构建成功，窄记录 seq_scan 增量为 0；固定样本日期的两轮定向补测及脱敏打包通过。
完整证据见[升级验证报告](../reports/v131-upgrade-2026-11-11.md)。
用户阅读 UPGRADE.html 的验收尚未确认；本原稿在实现合并后、正式制包前通过独立的文档 PR 定稿，
只有已完成的项目写入正式发布结论。

- 真实安装上的完整 `resume`：沿用恢复夹具覆盖；连接错误和 failed 单元命令继承 v1.3.0 实测。
  与本版真实迁移失败回滚的证据分别记录。
